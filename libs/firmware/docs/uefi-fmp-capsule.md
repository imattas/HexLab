# UEFI FMP capsule metadata inventory

Run `hexlab_cli firmware inspect <path> --format uefi-capsule` to inventory one contiguous EFI Firmware Management Protocol (FMP) capsule beginning at file offset zero. The CLI reports the EFI capsule header, FMP header counts, embedded driver extents, and each FMP image descriptor with image type GUID, image index, image and vendor-code sizes, absolute file offsets, and version 2/3 hardware-instance and capsule-support fields. To inspect an EFI_CAPSULE_TABLE-style list, pass each capsule as a separate path before the format option: `hexlab_cli firmware inspect <path1> <path2> --format uefi-capsule`. The CLI accepts up to 256 files and applies the 512 MiB cumulative input, 4096 cumulative item, and same-GUID checks; each capsule's reported offsets are local to that input file. Single-file output remains unchanged.

The parser accepts the standard 28-byte EFI capsule header or an extended header identified by `HeaderSize`, the FMP capsule GUID, FMP header version 1, and FMP image header versions 1 through 3. It checks declared bounds, ascending item offsets, descriptor sizes, cancellation, a 512 MiB input cap, and a 4096-item cap. For an extended EFI capsule header, the API and CLI report the exact opaque byte range between the fixed 28-byte header and `HeaderSize`; no assumptions are made about those extension bytes. The API also reports the number of input bytes after `ImageSize`, separately from the declared capsule extent. Malformed and unsupported structures return a diagnostic. Payload bytes, authentication structures, embedded drivers, and vendor data are never extracted, interpreted, or executed.

FMP capsules setting `CAPSULE_FLAGS_POPULATE_SYSTEM_TABLE` are rejected as malformed, as required by UEFI 2.10 §23.3.3. The three reserved bytes in every versioned FMP image header must also be zero. Other capsule flag bits remain metadata and are not interpreted by this parser.

The C++ API accepts a bounded EFI_CAPSULE_TABLE-style list of independent contiguous FMP capsule buffers. The CLI accepts the same list as multiple file paths. Both validate each capsule and apply the 512 MiB cumulative input, 4096 cumulative item, and 256 capsule limits. Item offsets are local to their corresponding buffer. This does not scan arbitrary file offsets or parse runtime scatter/gather block descriptors, validate signatures or payload authentication, decode firmware payload formats, process nested capsules, or update firmware.

The layout follows the [UEFI 2.10 capsule definition and FMP capsule structures](https://uefi.org/specs/UEFI/2.10/23_Firmware_Update_and_Reporting.html); the table's array count and same-GUID constraint follow the [UpdateCapsule() definition](https://uefi.org/specs/UEFI/2.10/08_Services_Runtime_Services.html#updatecapsule). The parser was also compared with EDK II's [FmpCapsule.h](https://github.com/tianocore/edk2/blob/master/MdePkg/Include/Guid/FmpCapsule.h), [DxeCapsuleLibFmp](https://github.com/tianocore/edk2/blob/master/MdeModulePkg/Library/DxeCapsuleLibFmp/DxeCapsuleLib.c), and [CapsuleDump](https://github.com/tianocore/edk2/blob/master/MdeModulePkg/Application/CapsuleApp/CapsuleDump.c). The [Ghidra Firmware Utilities](https://github.com/al3xtjames/ghidra-firmware-utils) document a related hierarchical loader for UEFI firmware volumes and nested FFS files/sections. That project does not describe FMP capsule parsing, so the capsule structures here follow the UEFI and EDK II references directly; only the general inventory practice of retaining nested item boundaries and metadata was relevant.
