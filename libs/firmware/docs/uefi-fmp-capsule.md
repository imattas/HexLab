# UEFI FMP capsule metadata inventory

Run `hexlab_cli firmware inspect <path> --format uefi-capsule` to inventory one contiguous EFI capsule beginning at file offset zero. The CLI recognizes both FMP capsules and the UEFI JSON capsule envelope. For FMP, it reports the EFI capsule header, FMP header counts, embedded driver extents, and each FMP image descriptor with image type GUID, image index, image and vendor-code sizes, absolute file offsets, and version 2/3 hardware-instance and capsule-support fields. For JSON, it reports the capsule ID, version, payload size, and offset while preserving payload bytes as opaque data. To inspect an EFI_CAPSULE_TABLE-style list, pass each capsule as a separate path before the format option: `hexlab_cli firmware inspect <path1> <path2> --format uefi-capsule`. Lists currently accept FMP capsules only, up to 256 files, and apply the 512 MiB cumulative input, 4096 cumulative item, and same-GUID checks; each capsule's reported offsets are local to that input file.

The FMP parser accepts the standard 28-byte EFI capsule header or an extended header identified by `HeaderSize`, the FMP capsule GUID, FMP header version 1, and FMP image header versions 1 through 3. It checks declared bounds, ascending item offsets, descriptor sizes, cancellation, a 512 MiB input cap, and a 4096-item cap. The JSON parser validates the same generic capsule extent and the version-1 `EFI_JSON_CAPSULE_HEADER` (exact nonzero payload extent); its payload is opaque and is not validated as UTF-8 or JSON. For an extended EFI capsule header, the API and CLI report the exact opaque byte range between the fixed 28-byte header and `HeaderSize`; no assumptions are made about those extension bytes. The API also reports the number of input bytes after `ImageSize`, separately from the declared capsule extent. Malformed and unsupported structures return a diagnostic. Payload bytes, embedded drivers, and vendor data are never extracted or executed.

For FMP image payloads beginning with the standard `EFI_FIRMWARE_IMAGE_AUTHENTICATION` and PKCS#7 `WIN_CERTIFICATE_UEFI_GUID` prefix, the parser validates the certificate header extent and reports the monotonic count, certificate range, and signed-data range. The reported payload offset skips this authentication prefix, while the descriptor's `image-size` continues to represent the full update-image size. It does not verify signatures, trust certificates, enforce monotonic freshness, or interpret certificate contents. Payloads that do not match the standard PKCS#7 certificate type remain opaque. This metadata follows the [UEFI 2.11 authentication structure](https://uefi.org/specs/UEFI/2.11/23_Firmware_Update_and_Reporting.html).

FMP capsules setting `CAPSULE_FLAGS_POPULATE_SYSTEM_TABLE` are rejected as malformed, as required by UEFI 2.10 §23.3.3. The three reserved bytes in every versioned FMP image header must also be zero. Other capsule flag bits remain metadata and are not interpreted by this parser.

The C++ API accepts a bounded EFI_CAPSULE_TABLE-style list of independent contiguous FMP capsule buffers. The CLI accepts the same list as multiple file paths. Both validate each capsule and apply the 512 MiB cumulative input, 4096 cumulative item, and 256 capsule limits. Item offsets are local to their corresponding buffer. This does not scan arbitrary file offsets or parse runtime scatter/gather block descriptors, validate signatures or payload authentication, decode firmware payload formats, process nested capsules, or update firmware.

FMP update-image payloads are also scanned for embedded PI firmware volumes. The inventory reports each volume's capsule-file offset, size, file-system GUID, revision, header-checksum state, and file/section counts. These offsets point into the original capsule; the payload is not copied or modified. Each capsule is bounded to 64 payload scans, 64 discovered volumes, 65,536 files, 65,536 sections, and 128 MiB of decompressed section data across all payloads. Capsule lists share those budgets across all inputs. Each scan gets at most one 64th of the decompression budget, bounding work even when a malformed earlier payload prevents accounting for partial decompression. An image with no recognized FFS2/FFS3 volume is a complete scan with zero results. If a parser error or exhausted budget prevents a scan from completing, capsule parsing remains available and marks that payload's embedded-volume scan incomplete with a diagnostic. Nested volumes that the PI parser does not recognize remain undiscovered.

The layout follows the [UEFI 2.11 FMP and JSON capsule structures](https://uefi.org/specs/UEFI/2.11/23_Firmware_Update_and_Reporting.html); the table's array count and same-GUID constraint follow the [UpdateCapsule() definition](https://uefi.org/specs/UEFI/2.10/08_Services_Runtime_Services.html#updatecapsule). The FMP parser was also compared with EDK II's [FmpCapsule.h](https://github.com/tianocore/edk2/blob/master/MdePkg/Include/Guid/FmpCapsule.h), [DxeCapsuleLibFmp](https://github.com/tianocore/edk2/blob/master/MdeModulePkg/Library/DxeCapsuleLibFmp/DxeCapsuleLib.c), and [CapsuleDump](https://github.com/tianocore/edk2/blob/master/MdeModulePkg/Application/CapsuleApp/CapsuleDump.c). The [Ghidra Firmware Utilities](https://github.com/al3xtjames/ghidra-firmware-utils) document a related hierarchical loader for UEFI firmware volumes and nested FFS files/sections. That project does not describe FMP capsule parsing, so the FMP structures here follow the UEFI and EDK II references directly; only the general inventory practice of retaining nested item boundaries and metadata was relevant.
