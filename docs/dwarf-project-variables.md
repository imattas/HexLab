# DWARF Project Variables

HexLab imports bounded ELF DWARF v4/v5 parameter and local-variable DIEs into the project database. Each row retains its stable project ID, owning function entry, name, optional project type ID, parameter/local flag, enclosing subprogram DIE offset, optional direct address, raw location-expression bytes, decoded operation operands, and full source DIE identity (`source_id`, section, unit offset, DIE offset, record size). Supported v5 variable location lists are retained as half-open PC ranges with the raw expression and decoded operations for every entry.

Import ownership is resolved by matching the variable's `scope_offset` to a function symbol's DWARF `record_offset` in the same source, section, and compilation unit. The function must map into the loaded image and already have a function-analysis root. Unscoped globals, unresolved scopes, out-of-image function records, variables with empty or over-limit names, and rows beyond the project record cap are skipped. Named types are linked where the existing DWARF type import produced a project type row; otherwise the variable remains visible with an unresolved type.

The v5 `.debug_loclists` subset accepts `DW_FORM_sec_offset` and `DW_FORM_loclistx`, plus `DW_LLE_base_address`, `DW_LLE_base_addressx`, `DW_LLE_start_end`, `DW_LLE_start_length`, `DW_LLE_startx_endx`, `DW_LLE_startx_length`, and `DW_LLE_offset_pair`. Indexed address entries require the compile unit's validated `DW_AT_addr_base` and a bounded DWARF v5 `.debug_addr` contribution. Address indices and computed half-open ranges are checked for contribution bounds, overflow, and empty or reversed ranges. Default locations, split/compressed DWARF, and unsupported entry opcodes are rejected with the importer's bounded-error policy. The importer preserves raw expression bytes and decoded `DW_OP` operations. It derives a signed CFA-relative offset for `DW_OP_fbreg` only when the enclosing subprogram has the direct frame-base expression `DW_OP_call_frame_cfa`; it also recognizes a direct `DW_OP_call_frame_cfa`, constant, `DW_OP_plus` expression. This remains an offset, not an absolute stack address. Other expressions remain unevaluated, including register, piece, dereference, and stack-value forms; the importer never reads registers or memory. A variable with no expression bytes is shown as unavailable because debug information may omit a location or contain an empty expression; this is not presented as a definite optimized-out result.

The desktop Variables table and detail pane choose the location-list entry containing the selected PC and show its range, raw bytes, and decoded operations. With no matching entry the view says no location covers the selected PC; with no selected PC it lists the ranges. A derived CFA offset appears as `CFA-0xN` or `CFA+0xN`, labeled frame-relative. This is source-location metadata only; the view does not convert it to a runtime address or claim that a variable is available at every point in its scope.

Schema version 4 adds `debug_variables`; version 3 projects migrate transactionally with an empty variable table. Schema version 5 adds the optional CFA-relative offset. Schema version 6 adds durable location-range payloads. The canonical project-state codec is version 5 and remains able to read versions 1 through 4. Variable rows participate in SQLite snapshots, transaction deltas, undo/redo, and project reopen. Duplicate source DIE identities are ignored on re-import.

Limits: 100,000 project variable rows, 1,024 UTF-8 bytes per name/source ID, 256 bytes per source section, 65,536 expression bytes and 4,096 operations across a variable’s location list, at most 4,096 ranges, at most 1 MiB encoded range payload per variable, and the existing 64 MiB aggregate project-state budget. Lexical block scope beyond the enclosing subprogram, runtime expression evaluation, and editable variable locations are not included in this milestone.
