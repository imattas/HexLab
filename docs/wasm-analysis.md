# WebAssembly module inspection and disassembly

HexLab detects standard WebAssembly v1 modules by the binary magic and version, including through the automatic loader recipe. The bounded loader checks section extents and non-custom section order, parses type/function/import/export vectors, verifies defined function and code body counts, validates local declarations, and rejects bodies without their final `end` operator. Inputs are capped at 256 MiB, vectors at one million records, names at 1 MiB each/16 MiB total, and expanded local declarations at ten million.

`ImageMetadata::wasm` retains imports and exports with their UTF-8 names, kind-specific indices, and source file offsets for the section payload and individual entry. Function imports retain their type-section index; the full function index space records imported types first and defined types after them. Function exports resolve their type index through that combined index space. The start section retains its function index and source offsets, then resolves the type through the same combined index space and requires the WebAssembly 1.0 start signature `[] -> []`. An out-of-range index, missing type, non-empty parameter/result signature, or trailing section bytes is rejected as malformed. CLI `inspect` and saved-project inspection report the resolved start function and type indices. The standard `name` custom section retains function names and local names with their subsection entry offsets; function-name indices must be valid and unique, and local-name indices must fall within the function's parameters and declared locals. Defined function names are used as image segment labels. Unknown name subsections and unrelated custom-section payloads remain opaque. Table and memory imports retain limits; global imports retain value type and mutability. Export indices are validated against the function, table, memory, and global index-space counts. Non-function exports retain their exact kind and index but do not yet link back to a full descriptor. Table, memory, and global definition sections are parsed enough to validate counts; global initializers are limited to MVP numeric constants and `global.get` expressions. Unknown import/export kinds and unsupported table reference/global initializer forms return explicit unsupported errors. Names are bounded to 1 MiB per string and 16 MiB total across parsed import/export/name-section names.

Each defined function's operator stream is mapped at offset zero in its own wasm32 address space. The mapped bytes begin after the function body's local declarations, so instruction offsets are function-relative and do not include section, body-size, or local-declaration encodings. Imported functions have no code mapping. Segment names identify the module-level function index.

The decoder recognizes WebAssembly 1.0 structured-control, call/local/global, memory, constant, and scalar numeric opcodes. Encoded immediates, including branch-label depths, are retained. Instruction offsets advance by the full encoded operator length. `inspect` and `disassemble` work for mapped function bodies. The bounded decompiler constructs CFG blocks for empty-result `block`, `loop`, `if`/`else`, `br`, and `br_if` forms and carries compatible operand-stack values through joins; see [WebAssembly function lifting](wasm-decompilation.md) for the supported subset and limits.

The data section retains each MVP active or passive segment's mode, memory index, offset-expression kind/value, byte count, and source file offsets. Payload bytes remain in the original source image and are not copied into metadata. `i32.const` and `global.get` offset expressions are accepted; active targets must reference an existing memory, and global references must be in range. The data-count section is retained and checked against the parsed data-segment count. Unsupported segment flags and offset-expression opcodes fail explicitly.

When the initial memory extent is known and all active data offsets are constant, the loader adds a separate wasm32 address space for the initial linear-memory image. Defined memories include zero-filled gaps and active writes; overlapping writes follow module order, so the last data segment supplies the final bytes. Initialized ranges point back to their original payload bytes. Imported memories expose only ranges written by the module because untouched bytes come from the host. If an active offset uses `global.get`, exceeds the declared initial extent, or would exceed mapping budgets, the loader retains metadata and reports why it omitted the memory view. CLI inspection reports its address-space ID, byte extent, and whether coverage is complete or limited to initialized ranges.

The element section accepts the MVP function-index encodings for active, passive, and declarative segments, validates referenced functions and tables, and retains segment offsets and source locations. Constant-offset active segments are applied in module order to a sparse initial table map; later elements replace earlier values at overlapping slots. Defined-table holes are null, while untouched imported-table slots remain unknown. Active `global.get` offsets and out-of-range segments keep their source metadata but suppress the reconstructed initial table map. CLI inspection shows bounded known slot-to-function mappings.

This is a container and disassembly foundation, not a complete WebAssembly validator. Unrecognized custom-section payloads remain opaque after their names. Imports/exports are metadata only: no linking or address binding is performed. Type-stack validation, branch-depth-to-byte-offset resolution, bulk-memory/SIMD/threads/GC proposals, and complete typed IR lifting remain unsupported. Multiple tables/memories and unsupported proposal encodings are rejected. Instructions whose encodings exceed the fixed 15-byte instruction record are conservatively unsupported.
