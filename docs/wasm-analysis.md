# WebAssembly module inspection and disassembly

Integer global initializers support a bounded extended-constant subset with
i32/i64 addition, subtraction and multiplication, retained instruction
provenance and exact raw-bit evaluation. See
[extended global constants](wasm-extended-global-constants.md) for typing,
host-global dependencies, limits and the narrower data/element offset subset.

HexLab detects standard WebAssembly v1 modules by the binary magic and version, including through the automatic loader recipe. The bounded loader checks section extents and non-custom section order, parses type/function/import/export vectors, verifies defined function and code body counts, validates local declarations, and validates every defined function's complete operator stream. Inputs are capped at 256 MiB, vectors at one million records, custom sections at 65,536 rows, names at 1 MiB each/16 MiB total, expanded local declarations at ten million, and a decoded operator at 15 bytes.

`ImageMetadata::wasm` retains imports and exports with their UTF-8 names, kind-specific indices, and source file offsets for the section payload and individual entry. Function imports retain their type-section index; the full function index space records imported types first and defined types after them. Function exports resolve their type index through that combined index space. The start section retains its function index and source offsets, then resolves the type through the same combined index space and requires the WebAssembly 1.0 start signature `[] -> []`. An out-of-range index, missing type, non-empty parameter/result signature, or trailing section bytes is rejected as malformed. CLI `inspect` and saved-project inspection report the resolved start function and type indices. Every custom section receives a bounded inventory record with its UTF-8 name, file offset at the section ID, encoded-body size (excluding the ID/size prefix), and payload offset/size in the original module. Payload bytes are not copied into metadata; custom data remains opaque unless a specific parser below recognizes it. CLI shows at most 128 rows and reports the omitted count. The standard `name` custom section retains function names and local names with their subsection entry offsets; function-name indices must be valid and unique, and local-name indices must fall within the function's parameters and declared locals. Defined function names are used as image segment labels. The tool-conventions `producers` custom section is retained as bounded field/name/version records with source entry offsets; unknown fields and tool names are preserved. It caps fields at 64 and values at 4096, shares the existing 1 MiB-per-name and 16 MiB total-name budgets, and ignores malformed or duplicate producer sections with an informational diagnostic without invalidating the module. The `target_features` custom section is retained as bounded `+feature`/`-feature` declarations with entry provenance. It accepts at most 4096 unique names, applies the shared 1 MiB-per-name and 16 MiB total-name budgets, and ignores malformed or duplicate sections with an informational diagnostic; declarations are descriptive and do not enable proposal operators in the loader. Table and memory imports retain limits; global imports retain value type and mutability. Export indices are validated against the function, table, memory, and global index-space counts; exports also resolve their function type, table/memory limits, or global type and mutability. CLI `inspect` and saved-project inspection display up to 128 import and 128 export descriptors, including names, kind-specific indices, resolved function type indices or table/memory limits/global type and mutability, plus entry provenance; larger lists report the omitted count. Table and memory definition sections retain bounded limits; global definitions retain typed initializer expressions and provenance. Unknown import/export kinds and unsupported table reference/global initializer forms return explicit unsupported errors. Names are bounded to 1 MiB per string and 16 MiB total across parsed import/export/name/producers/target_features-section and custom-section names.

The `name` custom section also retains the optional module-name subsection, indirect label-name maps (subsection ID 3), and indexed type, table, memory, global, element-segment, and data-segment name maps (subsection IDs 4 through 9). Label rows preserve the function index, label index, UTF-8 name, and source entry offset; function indices must resolve in the final function index space, and duplicate function maps or `(function, label)` entries are rejected. Label indices are descriptive debug metadata and are not yet resolved against decoded control-flow labels. Indexed-name rows record their index, UTF-8 name, subsection kind, and source entry offset; indices are checked against the final corresponding module index space after all standard sections are available, and duplicate indices within a map are rejected. CLI inspection reports at most 128 module/index/label-name rows with omitted counts. These names do not change execution semantics. The subsection layouts follow the [WebAssembly extended name-section convention](https://github.com/WebAssembly/extended-name-section/blob/main/document/core/appendix/custom.rst).

The combined imported-then-defined `globals` metadata retains each global's type, mutability, section/entry offsets, and optional initializer. Numeric `i32.const`/`i64.const`/`f32.const`/`f64.const` initializers retain exact unsigned bits, preserving negative integers, signed zero, and NaN payloads without host floating-point conversion. A `global.get` initializer must name an earlier immutable global of matching type. Reads of imported numeric globals resolve when the caller's numeric-global resolver supplies raw bits; unresolved imports remain host-supplied. Reads of earlier defined numeric globals inherit their evaluated initializer bits when available. The same raw-bit result is available for numeric constants, including f32/f64, without converting through host floating-point values. Funcref globals accept `ref.null funcref` (with a bounded signed 33-bit heap type) and `ref.func` initializers. Function references are checked against the full imported-then-defined function index space after all sections are parsed. A global `ref.func`, function export, or element entry declares its target for body `ref.func` validation, as specified by the [WebAssembly module validation rules](https://www.w3.org/TR/2024/WD-wasm-core-2-20240811/#valid-module). Initializers end with exactly one result of the declared type; bounded integer extended expressions are described above. Other reference types and extended data/element offset expressions remain unsupported. CLI `inspect` and saved-project inspection display at most 128 globals with initializer kind, exact numeric bits or dependency/target index, and source offsets; resolved `global.get` values include their exact raw bits. Imported globals have no module initializer and are labelled host-supplied.

Each defined function's operator stream is mapped at offset zero in its own wasm32 address space. The mapped bytes begin after the function body's local declarations, so instruction offsets are function-relative and do not include section, body-size, or local-declaration encodings. Imported functions have no code mapping. Segment names identify the module-level function index.

Before mapping code, the loader type-checks WebAssembly MVP scalar operators `0x00..0xbf` and the implemented SIMD subset: v128 constants and memory accesses, shuffle/splat/lane forms, comparisons, integer and floating unary/binary operations, vector logic, integer extend/narrow/extended multiply, and integer lane shifts. non-trapping float-to-integer conversions in `0xfc` subopcodes `0..7`, bulk-memory operations in `8..11`, and funcref table operations in `12..17`, plus multi-value function and structured-control typing: up to 128 numeric function results, declared parameter/local types, imported/defined global types and mutability, direct and indirect call signatures, table and memory presence, memory alignment and reserved indices, numeric operands and conversions, and structured-control result vectors. Indexed block types are resolved through the type section when they have no parameters. Branch depths must resolve to a live label; loop labels take no values, while block/if/function labels take their declared result vector. A `br_table` must have matching target vectors. Stack underflow, excess values at `end`, invalid `else`, missing `end`, and bytes after the function's final `end` are malformed. Unreachable regions use polymorphic stack validation. Indexed block types with parameters and unsupported extension opcodes fail as unsupported; oversized branch tables and operators fail under the decoder's bounds. Body validation limits control nesting to 100,000 frames and the operand stack to one million values, returning a resource-limit error if either bound is reached. It checks cancellation at least once per 4,096 operators and reports cancellation distinctly. This validation establishes module-level type correctness, while the separate decompiler remains a narrower lifting subset.

The processor decoder recognizes WebAssembly 1.0 structured-control, call/local/global, memory, constant, and scalar numeric opcodes, including typed `select` with one numeric or `funcref` result type. It validates the signed block-type immediate against the supported negative value-type encodings, and requires the MVP `call_indirect`, `memory.size`, and `memory.grow` index immediates to be zero. Scalar load/store decoding retains memarg alignment and offset operands and rejects alignment exponents above the operation's natural access width. It also decodes `0xfc` table subopcodes `0x0c..0x11` (`table.init`, `elem.drop`, `table.copy`, `table.grow`, `table.size`, and `table.fill`) with bounded LEB128 indices, following the [WebAssembly bulk-memory and reference-types encodings](https://github.com/WebAssembly/spec/blob/main/proposals/bulk-memory-operations/Overview.md). For SIMD, the standalone processor decoder recognizes `v128.const` with its exact 16-byte payload, plus the v128 memory-access family (loads, extending and splat loads, store, lane loads/stores, and zero-extending loads), the complete lane extract/replace family (subopcodes `16..18`, `20..22`, `24..25`, `27..28`, `30..31`, and `33..34`), the no-immediate comparisons in subopcodes `0x23..0x4c` (integer i8x16/i16x8/i32x4 and float f32x4/f64x2), the packed integer add/subtract family (`i8x16` subopcodes `0x6e..0x73`, including signed/unsigned saturating variants; `i16x8` `0x8e..0x93`, including signed/unsigned saturating variants; and `i32x4.add`/`i32x4.sub` at `0xae`/`0xb1`), the binary floating arithmetic family (`f32x4` add through pmax at subopcodes `0xe4..0xeb` and `f64x2` add through pmax at `0xf0..0xf7`), the i8x16 unary/test family (subopcodes `0x60..0x64`: abs, neg, popcnt, all_true, bitmask), the i16x8 abs/neg/all_true/bitmask family at `0x80`, `0x81`, `0x83`, and `0x84`, the i32x4 equivalents at `0xa0`, `0xa1`, `0xa3`, and `0xa4`, the i64x2 abs/neg/all_true/bitmask family at `0xc0`, `0xc1`, `0xc3`, and `0xc4`, and the no-immediate vector-logic operators `v128.not`, `v128.and`, `v128.andnot`, `v128.or`, `v128.xor`, `v128.bitselect`, and `v128.any_true`. It also decodes integer SIMD lane shifts `i8x16`, `i16x8`, `i32x4`, and `i64x2` `shl`, `shr_s`, and `shr_u` with no extra immediates. SIMD 1.0 defines no i64x2 comparison operators. Lane immediates are retained as 8-bit operands, bounds-checked against the lane count, and shown in formatted output. Memory operators retain memarg alignment/offset operands, validate each alignment against the access width, and check lane indices against the selected lane width, following the [WebAssembly SIMD binary encoding](https://github.com/WebAssembly/simd/blob/main/proposals/simd/BinarySIMD.md). The 16-byte `v128.const` payload is retained as two 64-bit operands and rendered from its original encoded bytes. The module validator and decompiler share the documented SIMD subset of v128 constants and memory operations, shuffle/swizzle/splat/lane operators, comparisons, integer and floating arithmetic, vector logic, integer unary/extend/narrow/extended-multiply forms, and integer lane shifts. Other decoded SIMD operators, including SIMD conversions and relaxed SIMD operations, remain outside validated lifting. Encoded immediates, including branch-label depths and the supported `ref.null funcref` heap type, are retained, and instruction offsets advance by the full encoded operator length. Module validation accepts `0xfc` subopcodes `0..17`: scalar conversions, bulk-memory operations, and the six table operations. It also validates typed `select`'s single result type and exact operand types. Table-operation validation checks table and element indices, requires exactly one funcref table at index zero, and verifies each i32/funcref operand stack shape. The table operations are available in validated module disassembly; the decompiler still rejects them because it does not model table mutation or table effects. `inspect` and `disassemble` work for mapped function bodies. The bounded decompiler constructs CFG blocks for supported `block`, `loop`, `if`/`else`, `br`, and `br_if` forms and carries compatible operand-stack values through joins; see [WebAssembly function lifting](wasm-decompilation.md) for the supported subset and limits.

The data section retains active and passive segment modes, memory indices, offset-expression kind/value, byte counts, and source file offsets. Payload bytes remain in the original source image and are not copied into metadata. Active targets must reference an existing memory. See the extended i32 segment-offset section for accepted offset expressions. The data-count section is retained and checked against the parsed data-segment count. Unsupported segment flags and offset-expression opcodes fail explicitly.

When the initial memory extent is known and all active data offsets evaluate to constants, the loader adds a separate wasm32 address space for the initial linear-memory image. Defined memories include zero-filled gaps and active writes; overlapping writes follow module order, so the last data segment supplies the final bytes. Initialized ranges point back to their original payload bytes. Imported memories expose only ranges written by the module because untouched bytes come from the host. If an active offset remains unresolved, exceeds the declared initial extent, or would exceed mapping budgets, the loader retains metadata and reports why it omitted the memory view. CLI inspection reports its address-space ID, byte extent, and whether coverage is complete or limited to initialized ranges.

The element section accepts both legacy function-index vectors and expression-form element encodings (flags 0 through 7). Expression vectors retain exact `ref.func index; end` and `ref.null funcref; end` initializers; their reference type must be `funcref`. Null entries clear earlier active table values in module order. This allows active, passive, and declarative expression-form segments to participate in the same index validation, table initialization, and `table.init` checks as legacy segments. Other initializer expressions and non-`funcref` segment types remain explicitly unsupported. The loader validates referenced functions and tables and retains segment offsets and source locations. See the extended i32 segment-offset section for active offset expressions. Constant-evaluated active segments are applied in module order to a sparse initial table map; later elements replace earlier values at overlapping slots. Defined-table holes are null, while untouched imported-table slots remain unknown. Unresolved offsets and out-of-range segments keep their source metadata but suppress the reconstructed initial table map. CLI inspection shows bounded known slot-to-function mappings.

Export records resolve through their kind-specific index spaces. Function exports retain the function type; table and memory exports retain their declared limits whether imported or defined; global exports retain the numeric value type and mutability. The export's name, kind, index, entry number, and file provenance remain available, so consumers do not need to rescan imports or infer an exported descriptor from another address-space view.

Function recovery adds distinct provenance seeds for exported defined functions. Each seed points back to the validated export row and its resolved function type, and is accepted only when the corresponding function-relative code segment remains fully initialized and executable. Imported function exports remain external. See [WebAssembly exported-function roots](wasm-function-roots.md) for the cache and validation details.

`WasmMetadata::globals` retains imported globals first and defined globals second, with each supported value type, mutability, initializer, and source provenance. Bounded MVP element mappings remain available for optional table-slot hints; dynamic indirect calls retain their runtime table index and do not require a complete table reconstruction.

This is a bounded MVP body validator and disassembly foundation, not a complete WebAssembly validator. `link_wasm_inventory` adds offline module-inventory comparison over explicitly supplied identities and parsed metadata. It matches import module/name/kind to a unique export, checks complete function parameter/result vectors, table/memory limit subtyping, and exact global type/mutability, and reports missing, ambiguous, incompatible, unsupported, or invalid-inventory rows. Default bounds cap inventories at 4,096 modules, 1,000,000 imports, and 16,000,000 export comparisons; callers may configure them. Cancellation returns rows accumulated so far. It never opens or auto-loads modules, instantiates them, binds executable addresses, or executes host code; tags/proposal kinds are not represented and remain unsupported. Unrecognized custom-section payloads remain opaque after their names. Imports/exports are metadata-only except for an optional caller resolver for numeric imported globals: it receives each global import descriptor and can return exact raw bits (i32/f32 are limited to 32 bits; i64/f64 use all 64 bits); returning no value leaves it host-supplied and unresolved. Resolved bits are retained on the corresponding imported `WasmGlobal`. Resolver calls occur only after structural/module validation, and resolver exceptions or out-of-width values fail loading. Function imports and funcref globals remain unresolved. An optional table/memory host-facts resolver checks imported funcref type, memory64 status, and host minimum/maximum/shared limits against the module's declared import limits; missing host facts are reported as unresolved import diagnostics. Compatible facts do not instantiate the module, bind executable addresses, or provide actual table contents or memory bytes. SIMD decoding is broader than module validation and lifting: the loader and lifter support a bounded MVP subset of v128 memory, lane, shuffle/swizzle/splat, comparison, integer and floating arithmetic, vector-logic, extend/narrow, and integer-shift operators documented in the lifting reference. Threads/GC proposals and complete typed IR lifting remain unsupported; only non-trapping float-to-integer conversions and the listed bulk-memory subopcodes are enabled from their extension opcode space. Branch depths are validated against live structured labels by the loader and resolved to CFG labels by the bounded scalar lifter. Multiple tables/memories and unsupported proposal encodings are rejected. The standalone processor decoder accepts WebAssembly operators up to 32 encoded bytes; the bounded module validator still caps an operator at 15 bytes.

The function validator accepts non-trapping float-to-integer conversion operators in `0xfc` subopcodes `0..7` with exact source/result stack typing; bulk-memory operators in `8..11`; and table operations in `12..17`. Table initialization/drop indices are checked against the complete element section, table indices are checked against the single supported funcref table, and all table operation operands and results are type-checked. Dynamic table contents and mutation remain runtime state and are not applied to the loader's initial table view.

## Function discovery from element segments

Function recovery adds a local function root for every validated defined-function
reference in an element segment, including active, passive, and declarative
segments. This conservatively preserves possible table-dispatch targets even
when the function is not exported, the table is imported, or runtime code later
mutates the table. Imported functions remain host-provided and are skipped.
Each root records the element section/entry offsets, segment/element indices,
function/type indices, and local body file offset. A malformed or incomplete
local body is retained as an analysis candidate instead of becoming code.
This does not instantiate tables, resolve host callbacks, or model later table
mutation.


## Imported table and memory compatibility

`load_wasm` accepts an optional caller resolver for imported table and memory compatibility facts after section, index-space, export, and function-body validation. Table facts include the reference type and limits; only `funcref` module tables are currently supported. Memory facts include limits, shared status through `WasmLimits`, and a memory64 flag. A memory64 import encoding is rejected as unsupported because the loader maps wasm32 address spaces only. Host minimums must be at least the module's required minimum; when the module declares a maximum, the host must also declare a maximum no greater than it. Shared status must match, and host memory limits must remain within the 65,536-page wasm32 ceiling. Invalid facts or incompatible limits fail loading; absent facts retain the import metadata and add an informational diagnostic. A compatible descriptor is only a type/limits check: function/table/memory runtime binding, imported table contents and host memory bytes remain external.

The loader can also accept caller-supplied symbolic host mappings. The optional function resolver maps function imports to a nonempty symbol (at most 4096 bytes) and a complete `WasmFunctionType`; parameter and result types must match the imported module type exactly. The table/memory facts resolver may include an optional symbol of at most 4096 bytes, retained on the import descriptor only after its limits and reference type pass compatibility checks. A numeric-global resolver may supply exact raw bits for an imported i32, i64, f32, or f64; those bits can feed constant initializer evaluation but do not provide a runtime global object. Each import records a resolution state: `unresolved` when no matching resolver returns accepted evidence, `compatible-host-facts` when a table/memory descriptor passes type and limits checks without a symbol, `symbolic-host-binding` when an accepted symbolic name is present, or `supplied-global-value` when numeric global bits are accepted. CLI inspection displays this state and any mapped symbol as `resolution` and `host-binding`. Resolvers see the fully validated descriptor, are invoked only for their matching import kind, and are never backed by ambient process/library lookup. None of these states bind executable callbacks or addresses, instantiate a module, supply imported table contents, or supply imported memory bytes; unresolved imports remain explicitly unresolved.

Analysis classifies `call` and `call_indirect` as call instructions so both retain their sequential continuation and appear in the caller's call-site inventory. A direct call creates an edge to a local defined function only when its index and type resolve through the validated combined function index space and its complete initialized executable body maps to the expected function address space. Calls to imported functions retain a symbolic external identity with the exact module, name, function index, and optional host binding; this identity is persisted in call facts and reference indexes, and appears on external nodes in function-call graph JSON. It never supplies an executable address. For references, `call_indirect` can resolve only when an immediately preceding validated `i32.const` supplies the selector, the instruction names table zero, the module has one complete local table that is neither imported nor exported, the full recovered function set contains no opaque instructions or table mutations, and the initial slot contains a function with the required type. Defined functions resolve to their validated function address space; imported functions retain symbolic module/name/index/host-binding identity. Dynamic selectors, null or out-of-bounds slots, incomplete scans, and tables whose contents could change remain unresolved. Function-call graph analysis records a target for the same bounded case after ownership recovery: a defined target receives its stable callee ID, while an imported target remains symbolic. This target proof uses the same whole-module completeness, fixed-table, slot, and type checks; it does not infer a runtime target from a dynamic selector. Full runtime table state and host callback execution are not modeled. Derived-cache version 82 and reference payload version 19 include imported identities. Function start-section roots identify code that runs during instantiation, but instantiation side effects and host callback execution are not modeled.

## Extended i32 segment-offset expressions

Active data and element offsets accept the extended-constant-expression i32
subset: `i32.const`, `global.get` of an earlier immutable i32 global, and
`i32.add`, `i32.sub`, or `i32.mul`, followed by the required `end`. The loader
validates operand types and stack shape, retains the expression's instruction
opcodes, immediates, and file offsets, and evaluates it when every referenced
global has known bits. Imported globals therefore remain unresolved unless the
numeric global resolver supplies their raw i32 value. Resolved offsets feed the
initial table and memory views; unresolved offsets preserve segment metadata
and suppress reconstruction of the corresponding initial view. Each
expression is bounded to 256 instructions and the module shares a one-million
constant-instruction budget. Other extended-constant opcodes and non-i32
segment offsets remain unsupported.

## Standalone `br_table` selection

The processor header `wasm_semantics.hpp` provides `evaluate_wasm_br_table`
for a decoded `br_table`. It validates the WebAssembly 1.0 instruction shape,
uses the supplied unsigned i32 selector to choose an indexed label depth, and
selects the final default depth when the selector is outside the case range.
Label depths are returned as structured-control indices; they are not code
addresses. Label resolution, stack popping, edge projection, and control-flow
state remain caller-owned.

`evaluate_wasm_select` evaluates the decoder's untyped and numeric typed
`select` forms from caller-supplied raw values and an i32 condition. A nonzero
condition chooses the first value, and W/i32/f32 results are zero-extended to
32 bits. Typed `funcref` select is decoded but not evaluated here. The helper
does not pop or mutate the operand stack.

`evaluate_wasm_integer_conversion` evaluates the decoded integer wrap/extend
and sign-extension bytecodes `i32.wrap_i64`, `i64.extend_i32_[su]`,
`i32.extend{8,16}_s`, and `i64.extend{8,16,32}_s`. It returns the exact result
bit pattern and destination width after validating the one-byte, operand-free
instruction form. Source sampling and operand-stack updates remain caller-
owned; trapping float conversions and saturating float-to-int conversions are
not part of this helper.

`evaluate_wasm_integer_bit_count` evaluates `i32/i64.clz`, `i32/i64.ctz`, and
`i32/i64.popcnt` from raw values after checking the decoded one-byte
operand-free form. Zero input produces the operand width for CLZ/CTZ and zero
for population count. The helper returns the integer count; stack mutation,
value sampling, and method execution remain caller-owned.

Tool-conventions `reloc.*` sections have a separate bounded metadata parser;
see [WebAssembly relocation metadata](wasm-relocation-metadata.md). It records
supported relocation rows and provenance but does not apply relocations.
