# JVM classfile analysis

The built-in JVM loader reads one bounded classfile (not a JAR). It retains the constant pool, class/super/interface names, fields, methods, and each method's `Code` bounds, max-stack/max-locals values, and exception table. Every nonempty `Code` array maps into its own 32-bit, byte-addressed address space so branch offsets are method-relative.

`Code` metadata also retains bounded, expanded `StackMapTable` verifier frames, including object constant-pool identities and uninitialized-object offsets. See [JVM StackMapTable metadata](jvm-stack-map-tables.md) for the public model, instruction-boundary checks, resource bounds, and distinction between parsed frames and full verification.

Class metadata also retains `Record` component names and descriptors (including a component's optional generic `Signature`), `NestHost`/`NestMembers`, and `PermittedSubclasses`. These attributes validate their declared extents and every referenced constant-pool entry. Each supported class attribute may appear at most once; list counts are bounded at 8192. Unknown nested Record component attributes are extent-checked and mark metadata incomplete. This metadata is descriptive: it does not yet synthesize Java record methods, prove nestmate access, or link permitted classes across classfiles.
The CLI's class summary prints these retained attributes and record component signatures.

The parser accepts classfile major versions 45 through 70, a 512 MiB input, at most 8192 fields/methods and attributes per owner, 8192 exception handlers per Code attribute, 64 MiB per attribute, and 256 MiB total attribute payloads. It parses standard constant-pool tags 1, 3–12, 15–20, including two-slot long/double entries. Unknown constant-pool tags, malformed indices, invalid modified UTF-8, out-of-range code/handler extents, and oversized metadata fail closed. Unknown attributes are skipped within their validated extent and mark metadata partial.

The decoder covers standard JVM opcodes through `jsr_w`, including `wide`, `tableswitch`, and `lookupswitch`. Switch tables are limited to 1024 entries/pairs and a decoded instruction may span up to the JVM `Code` limit of 65,535 bytes. Full encoded lengths and bytes are retained through function IDs, derived caches, incremental validation, graph fingerprints, and CLI byte display. Switch parsing validates alignment padding, table bounds, sorted lookup keys, and that targets lie outside the switch encoding. Reserved/implementation-dependent bytecodes and malformed or overflowing branch targets are unsupported/invalid. Method code is ordinary classfile bytecode and is never executed.

The typed common-IR lifter supports null and integer/long/float/double constants, primitive and reference local loads/stores through local index 255, `iinc`, category-1 `pop`/`dup`/`swap`, bounded object and one-dimensional array allocation, typed primitive/reference array loads and stores, `arraylength`, common scalar arithmetic (integer divide/remainder fail closed because trap effects are not modeled), numeric conversions, conditional primitive comparisons, `goto`/`goto_w`, and typed/void returns. Array operations validate stack operand types and preserve array/index/value ordering as JVM intrinsics with conservative heap read/write effects; loads and `arraylength` return opaque values of the bytecode's JVM stack type. `newarray` validates primitive type codes, while `anewarray` resolves its element class name from the constant pool. When classfile metadata is supplied, field access and `invokevirtual`, `invokespecial`, `invokestatic`, and `invokeinterface` decode their validated constant-pool descriptors to consume correctly typed stack values. Field operations remain typed and symbolic with unknown memory effects because resolution and static initialization can run code; method operations retain the symbolic owner/name/descriptor, ordered operands, unknown memory effects, and a typed opaque result when non-void. They do not claim virtual dispatch resolution or execute class code. Reference local values use an opaque 32-bit pointer type. The CLI, desktop pseudocode, and project automation paths pass loaded JVM metadata to the lifter.

The lifter transports nonempty operand stacks through versioned definitions and phis. Primitive joins/backedges require exact stack heights and value categories. Reference-bearing joins/backedges additionally require an explicit matching StackMapTable frame and exact incoming reference/local identities, including distinct uninitialized allocation offsets; missing or incomplete evidence fails closed. See [JVM stack transport](../libs/decompiler/docs/jvm-stack-transport.md) for the supported proof and remaining verifier limitations. Category-checked `pop2`, `dup*`, `dup2*`, and `swap` preserve logical category-2 values. The lifter lowers `tableswitch` and `lookupswitch` into switch dispatches after checking decoded CFG targets; exception edges retain ordered handler-dispatch metadata. Analysis and lifting conservatively classify `ldc`, `ldc_w`, and `ldc2_w` as throw-capable because reference and dynamic constants can trigger resolution or bootstrap behavior, and unknown constant kinds must retain exceptional coverage. A method whose exception-table scan exceeds the bounded CFG handler budget carries an explicit unsupported stop and is rejected by the JVM lifter; its partial handler edges are never presented as complete decompilation. Unsupported `ldc` kinds, legacy `jsr`/`ret` and unknown effects remain unsupported. `invokedynamic` call sites and dynamic constants retain their names, descriptors, bootstrap indices and constant-pool identity, but bootstrap behavior is not resolved or executed. JVM division/remainder still fail closed because trap effects are not modeled.

Constructor reference tracking initializes aliases of a verifier-proven `new` object after its exact-class `<init>` call. In a method named `<init>`, it also initializes aliases of `uninitializedThis` after a void `invokespecial <init>` to the current class or its direct superclass. The resulting normal-path identity is the current class; a failed constructor call clears its uninitialized receiver aliases in exceptional locals. Exception dispatch retains every protected throwing instruction in the source block, preserves distinct ordered catch clauses to one handler, and formats each handler edge with its throwing sites. A handler's caught-object identity is retained when all clauses agree exactly, when one catch type is the current class and the other its recorded direct superclass, or when catch-all clauses join as `java/lang/Throwable`. Other mixed catches remain unknown because external and transitive class hierarchy metadata is unavailable. Each exceptional edge contributes only its throwing instruction's local reference snapshot to the handler entry. Handler stacks contain exactly the caught reference; source operand stacks are discarded. StackMapTable frames constrain these facts without creating missing identities.

Memory SSA uses the instruction's input version for array loads/stores, `arraylength`, `athrow`, and primitive `ldc` forms, whose exceptional exits do not publish a successful write. Other supported throw-capable operations use an unknown memory effect, including resolution, allocation, invocation, type checks, monitor operations, and fields; the handler receives that unknown version rather than a claimed precise pre-throw or successful post-write state. A handler gets an explicit memory phi even for one exceptional predecessor. Independent memory partitions are disabled for functions with these edges until their renamer can select instruction-specific inputs. Exception edges still remain explicit metadata, and structured output falls back rather than claiming reconstructed try/catch source.

The CLI `--format jvm` and automatic classfile detection are wired through durable project loading. `CAFEBABE` also identifies Mach-O FAT32; detection chooses JVM only when the big-endian major-version field is 45–70, otherwise it remains a Mach-O candidate.

The lifter's supported object and constant operations are detailed in [JVM object and constant operations](jvm-object-and-constant-operations.md).
