# x86 scalar condition, arithmetic, and move semantics

Decoded short `70`–`7F` and near `0F 80`–`0F 8F` Jcc instructions carry an optional typed `X86Condition` alongside the original numeric condition field. The enum follows the architectural low-nibble encoding order, and `evaluate_x86_condition` evaluates each predicate from CF, PF, ZF, SF, and OF. The decoder continues to report the flags register as a read dependency; conditions do not imply writes to status flags.

Coverage tests exhaust all 16 condition codes over the 32 possible combinations of those five input flags, then check short and near opcode decoding preserves the corresponding typed condition. `evaluate_x86_arithmetic` supplies pure scalar semantics for ADD, ADC, SUB, SBB, CMP, AND, OR, XOR, and TEST at widths 8 through 64 bits. `evaluate_x86_arithmetic_instruction` connects a decoded instruction's opcode and first-operand width to that evaluator; callers supply the operand values and incoming carry/borrow. It returns the masked arithmetic result and CF/PF/ZF/SF/OF values; logical operations clear CF and OF. AF and other architecturally undefined flags are intentionally not represented by `X86Flags`.

These helpers provide condition and arithmetic primitives for instruction lifting; the current processor library does not yet expose a complete x64 instruction executor or unified lifted IR. The decoded-instruction adapter accepts only x86 and x86-64 contexts so architecture-neutral opcode values from other decoders cannot be misinterpreted as x86 semantics.

`evaluate_x86_data_move_instruction` evaluates decoded MOV, MOVZX, MOVSX, and MOVSXD records. It derives operand widths from the typed operands, reads immediate values from the record (including C7's sign-extended imm32 form), and accepts caller-supplied values for register and memory sources. It masks ordinary MOV values to the destination width and applies zero or sign extension for the extension forms. MOVSXD is restricted to its 32-to-64-bit long-mode form. This value helper does not access a machine state or read/write memory itself; the decoded instruction still carries the register and memory effects used by analysis and disassembly clients.

`evaluate_x86_multiply` computes unsigned or two's-complement signed full products at 8/16/32/64-bit operand widths and returns the low and high halves. For MUL and IMUL, CF and OF are defined and equal: they indicate whether the high half is a zero extension (unsigned MUL) or a sign extension (signed IMUL) of the low half. PF, ZF, and SF are marked undefined; AF is not modeled. `evaluate_x86_multiply_instruction` selects the operation and width from decoded MUL/IMUL records while taking the runtime operand values from its caller.

The decompiler also lifts x86-64 one-operand `MUL` and `IMUL` with typed full-product, low/high accumulator-pair, and CF/OF output formulas; see [implicit multiply lifting](x86-implicit-multiply.md). Other arithmetic flags remain unspecified.

`evaluate_x86_divide` accepts a width-sized high:low dividend and divisor for DIV/IDIV and returns width-sized quotient and remainder only on success. Divide-by-zero and quotient overflow (including signed minimum divided by minus one) return explicit statuses with both result-valid bits false. The decoded adapter derives operation and width from DIV/IDIV. Arithmetic status flags after DIV/IDIV are architecturally undefined and are not assigned guessed values by this API. Invalid operand widths and unrelated or malformed decoded instruction shapes return `nullopt`.

The decompiler also lifts x86 `ADD`, `SUB`, `AND`, `OR`, `XOR`, and scalar shifts with a memory destination into a read-modify-write store. The stored expression reads from the same effective address that receives the result, preserving the decoded memory width. Register/immediate flag producers carry condition predicates across acyclic CFG edges. At a join, propagation continues only when every predecessor carries state from the same producer instruction; equal-looking operations produced separately on different paths stay opaque because this pass cannot prove their register values agree. Loop components, calls, opaque instructions, and overwritten source registers or flags invalidate propagation.

`ADC` and `SBB` are lifted as explicit effects with the old destination, source, and incoming `carry_flag(flags)` as inputs; register destinations and status flags remain explicit definitions, and memory destinations keep a read/write memory effect. A following Jcc reads the resulting flags version, which incorporates carry-in or borrow-in. Register `INC` and `DEC` are lifted as typed unary intrinsics and preserve the old CF dependency; Jcc reads their resulting flags version. Register `NEG` is lifted as a typed unary intrinsic and Jcc reads its resulting flags version (CF is set for nonzero input; OF for the signed minimum). These Jcc predicates are available while the flag producer is preserved across the supported acyclic CFG path.

For ADC/SBB, INC/DEC/NEG and scalar shifts/rotates, Jcc predicates read the flags value produced by the instruction in register SSA. Shift and rotate predicates are emitted only when the requested flag bits are architecturally defined: known zero effective counts preserve the prior flags; known nonzero counts carry the opcode-specific definedness; variable-count shifts conservatively omit CF for byte/word operands and omit OF, while variable-count rotates omit OF. Other conditions remain the normal opaque `condition_N` branch tag. This preserves count masking and the architectural undefined-flag cases without guessing a concrete flag result.

`INC`, `DEC`, `NEG`, and `NOT` memory forms retain typed width, register effects, and read/write memory effects in the lifted intrinsic. This is not an instruction executor: memory access, faults, atomic ordering, and flag-bit materialization remain caller responsibilities. Memory-based compare-predicate reconstruction and arithmetic flag inference through loops remain outside the current pass.

The native x86 decoder also recognizes the implicit-address `MOVS`, `CMPS`, `STOS`, `LODS`, and `SCAS` families across 16-, 32-, and 64-bit execution modes. Their typed operands record each implicit memory reference and accumulator; register effects identify updated SI/DI and (with F2/F3) the address-sized count register. Direction-flag dependencies are exposed for pointer updates, while CMPS/SCAS write status flags and repeated compare/scan forms read them for their ZF stop condition. Source segment overrides are retained without applying them to MOVS/CMPS's fixed ES destination. Element widths and address widths are selected independently by operand/address prefixes and REX.W. Formatting uses the implicit `movsb`/`cmpsq` forms and exposes explicit segment overrides. `Instruction::flow` remains fallthrough after the instruction's internal repeated operation; consumers receive the repeat flavor and count/flag dependencies, while the decompiler still treats these operations as intrinsics rather than lowering their memory loop.

`evaluate_x86_shift_rotate` evaluates SHL, SHR, SAR, ROL, ROR, RCL, and RCR for 8/16/32/64-bit values. The caller supplies the already-read destination and incoming flags; the helper returns each modeled flag with a definedness bit and reports zero-count preservation explicitly. It applies the architectural 5-bit/6-bit count mask, then the rotate or carry-ring modulus. SHL/SHR/SAR compute the shifted value and PF/ZF/SF; CF is defined when the shifted-out bit is available; OF is defined only for count one; AF remains undefined. Counts beyond the operand width are conservatively reported as undefined. Rotates update CF and define OF only for count one, while preserving the other supplied status flags. The optional incoming AF value is separate because `X86Flags` intentionally contains only the five modeled condition flags.

`evaluate_x86_shift_rotate_instruction` accepts decoded x86/x86-64 scalar forms, reads an immediate count from the instruction record, and requires a caller-supplied byte count for the CL register form. The caller supplies a memory destination's value; neither helper reads memory or mutates a machine state. This is an instruction-family evaluator, not a complete x64 execution engine.

`evaluate_x86_setcc_instruction` evaluates a decoded `SETcc` to the byte value
zero or one from its typed condition code and caller-supplied CF/PF/ZF/SF/OF.
It validates the byte-register or byte-memory destination and decoded write
effects. It returns the value only; memory writes and register updates remain
caller-owned.

`evaluate_x86_cmovcc_instruction` evaluates decoded CMOVcc from a destination
value, source value, and incoming flags. A false condition preserves the full
destination; a true 16-bit write merges only the low word, while a true 32-bit
write in long mode zeroes the upper half. Memory-source forms require the
decoded read effect because the source is read regardless of the condition.
The helper returns the resulting destination bits but does not access memory or
commit registers.
