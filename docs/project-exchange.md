# Project analysis exchange

HexLab project exchange files use a bounded little-endian binary envelope. The four-byte magic is `HXEX`, followed by a 16-bit version, 16 reserved zero bits, the original input byte count, the original input SHA-256, and row counts. Version 1 contains three 32-bit counts, version 2 contains five, versions 3 through 5 contain seven, version 6 contains eight, version 7 contains nine, and versions 8 and 9 contain ten counts. Versions 1 through 8 remain importable. Current exports use version 9.

Records are stored in canonical order: annotations, bookmarks, explicit references, code/data regions, function decisions, type definitions, type assignments, then (in v6) scoped debug variables, (in v7) durable project breakpoints, and (in v8) byte-patch spans. Version 9 adds the persisted one-shot setting to each project-breakpoint row without changing category order. An address is encoded as a tag plus a 64-bit file offset; tag 0 preserves a file location and tag 1 represents a virtual address translated through the project image. Strings are UTF-8 byte sequences with 32-bit lengths. Region extents, function chunks, and debug-variable PC ranges must map contiguously to source bytes; destination addresses are resolved through the destination project's image mapping.

Version 2 transports annotations, bookmarks, explicit user references, code/data regions, function suppression/definition decisions, and explicit function chunks. Version 3 adds named type definitions and type assignments. Version 4 adds an optional DWARF source origin to each named type. Version 5 appends a checked declaration role (`type`, `object`, or `function`) after each type's optional origin. Version 6 appends scoped debug-variable rows after type assignments. Version 7 appends project-breakpoint rows after debug variables; each carries a virtual address mapped through its file offset, kind, size, enabled state, condition, logpoint flag and message, and configured ignore threshold. Runtime hit counts are session metadata and are not serialized. Version 8 appends canonical byte-patch spans after breakpoints. Each span carries its file offset, original bytes, and replacement bytes; original bytes are checked against the digest-bound input during both export and import, and executable contents are never embedded. Export refuses stale patch records instead of producing a bundle that cannot later pass source-byte validation. Import compares each incoming span with the destination's effective bytes: identical changes are skipped, `fail` rejects divergent overlaps, `skip` keeps the existing conflicting span, and `replace` applies incoming bytes. A conflicting span is handled as one record, while disjoint spans continue to import under `skip`. Patch rows are limited to 1 MiB each and use the same 16 MiB overall exchange cap. A debug-variable row carries its function entry, UTF-8 name, parameter flag, scope offset, optional type name, optional direct address, location-expression bytes and decoded operations, source origin, optional CFA offset, and ordered PC-scoped location ranges. Type references use names and source/function identity uses source-origin coordinates; project, database, type, function, breakpoint, patch, and entity IDs are never serialized. Function entries, direct addresses, breakpoint locations, patches, and non-default half-open PC ranges use file-relative mapping and are rebuilt through the destination image. Location expression and operation order are preserved; the `(UINT64_MAX, UINT64_MAX)` default-range sentinel remains unchanged. Exact enum numeric values travel in the existing canonical type body. Older exchanges default new definitions to `type` and preserve the destination role when replacing an existing definition. Type bodies use the canonical portable type codec; assignments refer to type names, and their locations use the same file-relative mapping as other records. The input size and digest must exactly match when importing. Records and nested function chunks are each limited to 100,000 total, each text field to 1 MiB, expressions to 64 KiB, each operation and range list to 4,096 entries, encoded range payloads to 1 MiB, conditions to 256 UTF-8 bytes, log messages to 1,024 UTF-8 bytes, and the complete exchange to 16 MiB. Unknown versions, reserved bits, invalid location/reference kinds, invalid type bodies or origins, missing assignment or variable types/functions, duplicate or noncanonical rows, truncation, trailing data, malformed operations/ranges, and out-of-range offsets are rejected.

Version 9 breakpoint rows also carry the configured one-shot flag. Runtime hit
counts remain local debugger metadata and are excluded. Older versions import
with one-shot disabled.

CLI examples:

```powershell
hexlab_cli project exchange export sample.hxproj --output sample.hxex
hexlab_cli project exchange import other.hxproj --input sample.hxex --conflict skip
```

The export command reports the number of rows written for each supported metadata kind, including regions, functions, project breakpoints, and byte patches.

Desktop workflow: open a saved, writable project, then choose **File → Export Project Metadata...** or **File → Import Project Metadata...**. The export dialog writes a `.hxex` exchange file. Import asks for a policy (`fail`, `skip`, or `replace`), then shows the row totals, identical rows skipped, and a conflict breakdown with example locations before applying. The complete imported command list is submitted through one actor operation and committed as one project transaction/history entry. The destination project assigns its own entity IDs. Exchange files are capped at 16 MiB, matching the CLI limit.

Desktop export stages the complete bounded exchange beside its destination and publishes it only after the write succeeds. Replacing an existing exchange is atomic, and protected project/source paths cannot be selected as the output target. A failed write therefore leaves the prior destination intact.

Import conflicts default to `fail`. `skip` leaves conflicting rows unchanged, while `replace` emits project commands for supported replacements. Those non-failing policies return an ordered conflict record for each single-valued annotation, bookmark, region, function, type-name, type-assignment, or debug-variable source-origin collision, including its destination location where applicable and the deterministic winner (`kept_existing` or `imported`). Identical rows are idempotently skipped and are not conflicts. Project breakpoints conflict by mapped address; `replace` updates configured fields while the destination retains its runtime hit count, and `skip` leaves the existing breakpoint unchanged. Debug-variable replacement retains the destination entity identity while replacing the imported source-origin row atomically. Distinct references with the same source and kind but different targets are valid set members: import retains both, emits a `preserved_both` conflict record naming the source and incoming target, and does not make that choice depend on input iteration order. All exchange record lists are canonical, so conflict records follow deterministic exchange order. Imported entities receive IDs from the destination project through its normal command path. Type definitions and their assignments are validated and committed as one workspace command so assignments use destination-generated IDs and cannot dangle. Planned type replacements also carry the exact before-row, including the canonical type body, source origin, and declaration role; changing that destination after planning causes a conflict at command validation.

Function records carry their complete explicit chunk list. Under `replace`, an empty incoming chunk list clears a destination-only explicit chunk override; importing a new function with no chunks leaves its default empty list intact.

Reference rows are the only metadata kind that supports a safe preserve-both merge. Annotations, bookmarks, regions, function decisions, and debug-variable source-origin identities each occupy a single-valued key; they require the caller's explicit `skip` or `replace` policy when values differ. The default `fail` policy keeps its transactional behavior and reports the first conflict as an error.

Collaborative edits use the history delta's `before` values as a three-way merge base. When a stale edit changes one annotation field while the current revision changed another, the collaboration API preserves both changes. Bookmark labels, type-definition fields, region extents/kinds, function entries/suppression/chunks, and explicit reference fields merge only where each side's intent is unambiguous. Type assignments rebase when identity and location remain stable and the destination type exists. Patch sets are merged byte by byte against the embedded original input: disjoint edits combine, equal replacements converge, and different replacements of the same byte remain explicit conflicts. A fully converged no-op proposal is acknowledged at the current revision without creating a redundant history step. Patch rebases inspect at most 64 MiB of combined changed ranges; larger proposals return a resource-limit error. Moves, overlapping range changes, unsafe structural edits, and unresolved type dependencies remain explicit conflicts. The merge never selects between different values for the same field or byte.

The desktop File menu's **Review Collaboration Proposals** dialog shows base, proposed, and current values for annotations, bookmarks, type definitions and assignments, regions, function decisions, explicit references, byte patches, debug variables, and project breakpoints. Patch descriptions cap displayed spans and bytes while retaining their file offsets. Before accepting or dismissing, the dialog synchronizes queued document edits and rereads the project head. It enables acceptance only when the database's shared rebase preview can construct an unambiguous resolution at that exact edit revision. Proposal-changed fields are applied while current-only changes are preserved; overlapping bytes, structural conflicts, or an intervening revision change keep acceptance disabled. Acceptance commits the resolved project delta and inbox status in one SQLite transaction, and a converged proposal can be accepted without adding a history step. Dismissal records the decision and keeps current project data. Debug-variable and project-breakpoint proposals remain inspectable but require a domain-specific resolution flow.
