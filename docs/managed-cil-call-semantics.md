# Managed CIL call semantics

The managed signature catalog resolves `MethodDef`, `MemberRef`, `MethodSpec`, and supported `StandAloneSig` call tokens with bounded parameter counts and metadata table/heap checks. Method definitions inherit their owning `TypeDef`; member references resolve supported TypeDef, TypeRef, TypeSpec, and MethodDef parents. A closed generic TypeSpec parent carries its type arguments, and MethodSpec carries its method arguments, so call typing substitutes known `VAR` and `MVAR` nodes without changing the original metadata tokens.

The CIL lifter preserves the evaluation-stack effects from the method signature: explicit arguments stay in source order, an instance receiver is retained as the first call operand, and `newobj` consumes only constructor parameters (it has no preexisting receiver). Receiver and indirect target operands are marked as references when their shape is known. Supported primitive, floating-point, reference, array, pointer, and closed generic argument and return types are propagated. `newobj` produces a typed managed reference when metadata proves the declaring type is a reference type; value-type construction remains opaque because the common IR has no aggregate-value type. `callvirt` and `newobj` reject signatures that omit the required instance receiver; `newobj` also rejects a non-void signature. Calls carry a token-based name and unknown memory effect. `call`, `callvirt`, `calli`, and `newobj` are distinguished in pseudocode, and call tokens remain in `referenced_tokens`.

Unknown signature element types stay unknown while the exact metadata parameter count still determines stack pops. If a call token has no usable supported signature (including native/runtime-only or unresolved targets), decompilation stops with `unsupported` because inventing an argument count or return stack effect would corrupt following control flow. The lifter does not model native ABI calls, vararg call-site optional argument rules, or unmanaged calling conventions. External TypeRef assembly identities are not bound to companion assemblies; most external TypeRef constructor results therefore remain opaque. Generic VAR parameters on open TypeDef owners and unresolved generic substitutions remain unknown.

The metadata type catalog also retains bounded in-module TypeDef base-class and InterfaceImpl edges. `managed_type_is_assignable` answers only proven reachability through local TypeDefs (including a direct token identity); external TypeRefs and unresolved TypeSpecs are not followed. This graph is available to analyses, but current CIL exception dispatch still emits an opaque runtime type-match predicate because the thrown object's dynamic type is not statically known. Virtual call targets also remain token-based: metadata does not by itself prove the receiver's concrete runtime type, and MethodImpl/slot dispatch is not yet modeled.
