# RISC-V data-reference validation

Decoded references support bounded RV32/RV64 address propagation. LUI seeds a sign-extended U-immediate value, and AUIPC seeds its signed U-immediate relative to its own PC. ADDI may add a signed immediate to a tracked register, while ORI, XORI, and ANDI apply their sign-extended immediates with XLEN-width bitwise operations; these values can flow across recovered CFG edges. ADDI with `x0` can seed an absolute immediate. A bitwise result becomes a reference only when the exact computed value maps into the instruction's address space. At a join, a value survives only if every predecessor proves the same address. Address facts may remain outside mapped segments while being built, but a typed `memory_address` reference is emitted only for a mapped target.

RV64 `ADDIW` also propagates a proven source or `x0` plus a signed 12-bit immediate using the architectural low-32-bit addition and sign extension to 64 bits. Its exact result can form a mapped immediate reference or feed later address arithmetic. RV32 does not accept `ADDIW`.

A later load or store using that tracked register resolves to the computed effective address. The target must remain inside a single mapped segment for the full access width, and the segment must have the required read or write permission. Invalid or permission-incompatible memory operands remain typed unresolved expressions. JALR calls and jumps resolve when their register-relative base is known and the resulting low-bit-cleared address is in an executable segment. Source instructions are already required to lie wholly in executable code according to the image code policy. Resolved references participate in the same indexed incoming/outgoing pages and canonical reference cache as other references.

The implementation drops a value when its register is overwritten and clears all propagated values across calls. A CFG join requires exact predecessor agreement; unknown entry paths contribute no facts. It resolves a bounded little-endian RISC-V `R_RISCV_PCREL_HI20` pair when a unique local label on `R_RISCV_PCREL_LO12_I` or `R_RISCV_PCREL_LO12_S` identifies the high relocation in the same target section. The decoded instructions must be an `auipc` plus a matching `addi`, integer load, or store using the high destination register. `addi` address formation can resolve directly; load/store references additionally require the propagated base register to retain the exact high relocation value at the access. The pair's target symbol must be defined and non-preemptible, both addends must be explicit, and the low addend must be zero. RV32 and RV64 are supported when their decoded instruction widths match the ELF class. Ambiguous labels, duplicate relocation fields, other low relocations, absolute HI20/LO12 pairs, missing symbol addresses, and incomplete register flow remain unresolved. General RISC-V/GOT/TLS relocation evaluation and Mach-O relocation-pair resolution are not provided. The label association and relocation roles follow the official [RISC-V ELF object-file specification](https://docs.riscv.org/reference/abi/v1.0/riscv-elf-object-files.html).

`tests/reference_tests.cpp` exercises literal RV32 and RV64 AUIPC+ADDI/load/store instruction bytes, address formation and effective addresses, data-segment indexing, writable/readable permission rejection, unmapped targets, non-executable source rejection and reference-index roundtrips. Cross-block predecessor agreement, JALR resolution, and PCREL_HI20/LO12 relocation-pair resolution still need focused regression fixtures. The function-analysis engine fingerprint includes the RISC-V bitwise-immediate address-flow revision so cached derived reference indexes that predate these propagation facts are recomputed. Existing reference payload encoding and identity rules are unchanged.
