# Mode-aware processors and x86-32 analysis

## Intent and authorization

Build the next working part of the original C++20/wxWidgets reverse engineering suite: x86-32 decoding, recovery, shared editing/search/graphs and persistent projects through the existing CLI and desktop. Keep the giant monorepo and separate tools/runtime DLLs. The user's standing instruction removes further approval checkpoints; write and execute focused specs/plans while preserving tests and review. This specification refines the already-approved architecture's stage 4, not the full product scope.

Stage 3 is verified and installed; its 39 headless/49 desktop tests remain regression requirements. Stage 4 is split into independently testable subprojects. This first subproject adds flat x86-32 instruction analysis and the processor dispatch/cache context needed by later targets. x86-16 segmentation/modes, ELF/Mach-O image/object loading, ARM/AArch64, type/ABI services, PDB/DWARF import and signatures remain explicitly required subsequent subprojects. A scalar decoder subset is never recorded as complete x86 family coverage.

## Current constraints

Architecture and execution-mode enums currently live in image.hpp; processors exposes only decode_x64(bytes,address), while analysis, cache validation, command gates, listing, raw loading and frontend arguments contain hard-coded x86-64 checks. PE32 metadata already identifies x86/32 and uses a 32-bit address space. The existing operand types can express 8/16/32/64-bit registers, encoded/effective immediates, segment overrides and memory address width, but Instruction lacks its decode context. Complete-derived caches validate raw bytes with decode_x64 regardless of image mode. These assumptions must change together before 32-bit analysis is enabled in the frontends.

No foreign decoder, graph engine or disassembler subprocess becomes a production dependency. ByteStorage, immutable snapshots, checked coordinates, source-bound jobs, actor-owned SQL, typed references, current-fact checks and optional-cache semantics remain authoritative. Keep unknown encodings explicit and preserve original x64 fixtures and native LEA execution checks.

## Chosen approach

Generalize the original x86 parser around explicit mode rules, keeping the public decode_x64 wrapper for source compatibility. Add decode_x86_32 and a mandatory-context decode_instruction entry. Share bounded byte cursors, prefix collection and scalar-family parsers; keep mode-sensitive operand/address/control-flow rules explicit. Separate copying an entire second decoder was rejected because fixes would diverge; integrating a foreign decoder was rejected because this project implements its own engines.

Move existing Architecture/ExecutionMode enum definitions, preserving their values, to core/architecture.hpp and re-export them through existing image headers. Add DecodeContext {architecture,mode,order} and a small ProcessorCapabilities value returned without byte reads or dynamic registration. Unsupported combinations, including x86-16 for now, retain explicit reasons. Capability names refer to decoder support, not decompiler or debugger support. Analysis eligibility migrates only when cache and recovery contracts are ready.

Instruction carries its explicit DecodeContext. RelativeOperand also carries effective target width, and Instruction.stack_value_width records the hidden pushed/popped value size (zero for non-stack operations); these prevent near/return prefix semantics from being lost in typed records. Unknown is the default for hand-constructed values; production decoders set it. Canonical cache records include and validate context. Existing format_instruction and register_name continue to use typed operands; mode is never inferred from mnemonic text or a pointer width. No new plugin ABI is promised by these C++ value APIs.

## x86-32 decoding contract

The initial implementation covers valid legacy-32 forms of the existing scalar families: moves/extensions/LEA, stack operations, integer arithmetic/logical/shift/rotate/multiply, direct and supported indirect near control flow, returns/traps/NOP/pause and the applicable landing-pad instruction. Unsupported far, privileged/system, x87, vector, unusual prefixes and unimplemented extensions stop explicitly. Each newly recognized form gets a coverage row and literal fixtures; no generic opcode range is declared supported from one example.

Default and overridden operand/address sizes, register banks, high-byte registers, ModR/M, SIB, displacement sign/width, no-base forms and the 16-bit effective-address matrix are interpreted from mode. Bytes with other meanings in 64-bit mode cannot be consumed as legacy-32 REX prefixes. Unsupported mode-specific opcodes cannot inherit a different 64-bit interpretation. Stack/IP/flags register effects use the correct context; data width and address width remain separate.

Direct near targets use the documented behavior for their actual operand size/form. Pin wrap/truncation and instruction-end arithmetic with literal boundary cases; do not substitute checked 64-bit addition for architectural target formation. A computed target can be outside the image and remains a typed unmapped target rather than invented mapped data. Address calculation and segment assumptions are explicit: preserve overrides and unresolved segment-dependent memory expressions; do not claim an unknown segment base has been resolved. Illegal/truncated/unsupported results remain distinct and all reads remain bounded to the architectural maximum instruction window.

Use primary ISA documentation for instruction interpretation: [Intel SDM landing page](https://www.intel.com/content/www/us/en/developer/articles/technical/intel-sdm.html), [Intel instruction reference](https://www.intel.com/content/www/us/en/content-details/851063/intel-64-and-ia-32-architectures-software-developer-s-manual-combined-volumes-2a-2b-2c-and-2d-instruction-set-reference-a-z.html), and [AMD general-purpose instruction manual](https://docs.amd.com/v/u/en-US/24594_3.37). Consult the actual relevant instruction pages during implementation, not secondary mnemonic tables. Record concrete page/revision and independently authored fixtures; do not copy implementation code or long manual passages.

## Analysis and persistence

All analysis decode paths use the same image-derived DecodeContext: reachable/function recovery, incremental memo validation, code/function decisions and worker manual listing. Current-key, manual-data, initialized-byte, overlap, ownership, budget and cancellation behavior are retained. References derive from typed operands; immediate search uses effective width; graph selection/layout and per-document source gates remain architecture-independent.

Bump the function-engine/cache format versions when context becomes part of canonical facts. Cache decoding receives the authoritative loaded-image context and rejects a mismatched serialized context before adopting facts. A checksum-recomputed payload that changes only processor mode must fail validation. Old cache rows are incompatible/recomputed, not interpreted as new records. User state, embedded input, UUID/history and schema version remain intact; adding decoder context does not require a user-schema migration. Byte edits to PE mode-bearing headers must select the new effective context and invalidate previous facts without discarding annotations.

Raw x86-32 recipes use Architecture::x86, ExecutionMode::x86_32, little-endian byte-addressed 32-bit coordinates, explicit base and optional entry. Reject invalid combinations and extents beyond the declared space, including invalid empty-input bases. Preserve existing raw x64 recipe byte representation. Accept new valid raw enum combinations in the canonical recipe validator; recipe/input keys and loaded-image context together prevent cross-mode cache adoption. PE32 effective metadata must reach the same services as raw-32.

## Frontends and distribution

Add canonical --arch x86-32 alongside existing --arch x86-64 to both raw CLI entrypoints. Metadata output reports architecture and execution mode separately. Add a native raw-mode choice with shared loader validation and captured dialog target; default remains x86-64. Existing project commands, names/comments, code/data/functions/chunks, undo/redo, patches/export, bounded search, references and CFG/call views work on 32-bit projects through shared actors. No GUI decoder or SQL calls are introduced.

Keep installed tools and engine DLLs together; no standalone executable substitution. New public headers are installed with existing targets. Full rebuild of all consumers follows public Instruction/context changes. BUILD_TESTING=OFF has no private checkpoints; headless builds fetch no wx dependency. Source and ledger remain in the existing unborn Git workspace; never invent identity or discard source.

## Acceptance

1. Cross-mode literal bytes demonstrate genuinely different lengths/registers/operands where required; all x64 corpus and execution-oracle tests remain green.
2. Legacy-32 scalar forms, size/address overrides, 16-bit address matrix, segment overrides, immediates, stack effects, relative targets and truncation/prefix/window limits have literal expected records and negative forms.
3. An independently compiled Win32 executable executes only authored safe probes for representative register/flag/address/stack behavior. It is a test oracle, never a production decoder or arbitrary-input executor. Failure to build/run it is reported, not silently called verification.
4. Raw-32 and PE32 recover literal functions/blocks/references, produce current CFGs and effective-width search hits, and retain unsupported/partial labels at real boundaries.
5. Code/data/function/chunk edits, patches/undo, source-missing reopen and exact export work on 32-bit projects with persistent history. Mode-changing effective header edits retire old facts and cached geometry.
6. A forged context with otherwise recomputed cache checksum is rejected against loaded-image mode; old caches recompute without touching user history; readonly behavior and optional cache errors remain correct.
7. Real CLI and wx workflows select explicit raw-32, navigate nonfirst results, switch a 32-bit and 64-bit document, edit/save/reopen and observe canonical matching bytes/addresses.
8. Full Debug desktop and Release headless suites, fresh disconnected/production builds, complete installed workflow checks and one fresh independent end-of-subproject review pass. Update variant-specific instruction/capability evidence; no broader-family claim.

## Review focus and limits

Pin mode confusion for 0x40-0x4F and 0x63, displacement-only versus IP-relative addressing, prefix ordering, stack operand size, branch target formation near address limits, 16-bit effective address combinations and mode-bearing patch/cache races. Existing short-read/alias/sparse-byte/readonly/export protections remain regression requirements. This stage has no type inference, decompiler, debugger, segmentation emulator or broad performance claim. Those remain later required work.
