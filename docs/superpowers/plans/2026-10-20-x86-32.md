# Mode-aware x86-32 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Execute inline; one fresh independent whole-subproject review at the end. Standing user authorization removes further approval checkpoints.

**Goal:** Add original x86-32 scalar decoding and usable analysis/editing projects through both installed frontends while preserving x86-64 behavior.

**Architecture:** Explicit immutable processor context drives decoder dispatch and canonical instruction/cache validation. Generalize the original x86 scalar parser around mode rules, then migrate analysis and frontend eligibility through shared capabilities. Existing actors, typed locations, history and source-gated views remain shared.

**Tech Stack:** C++20, existing CMake DLL targets, wxWidgets 3.2.12, vendored SQLite; separately built Win32 authored execution oracle for tests.

**Spec:** docs/superpowers/specs/2026-10-20-x86-32-design.md

## Global constraints

- Preserve the multi-tool/DLL monorepo and all existing tests. No production foreign decoder or disassembler subprocess.
- Windows x64 is the verified host; raw-32 means byte-addressed little-endian flat 32-bit coordinates. x86-16 remains explicitly unsupported in this subproject.
- CPU/mode identity is explicit and canonical. Unknown combinations stop rather than inherit x64 interpretation.
- Decode/parse stays off GUI handlers; SQL stays on actors; views gate session/source/presentation revisions.
- Cache incompatibility recomputes, never migrates or discards user history. A new decoder context does not change schema version 1.
- Full consumer rebuild follows public value ABI changes. Keep stage-3 installed prefix intact; eventual install uses out/install/X86ModeDebug.
- No new Git identity, commits, worktree cleanup, integration menu or approval pause. Maintain the ledger and preserve source on the existing unborn branch.

## Review focus

1. Bytes 0x40-0x4F and 0x63 must not acquire the wrong mode's meaning; task 3 owns cross-mode literal records.
2. Displacement-only/address-override/segment memory must not become a fabricated IP-relative address or reference; tasks 3 and 5 pin these cases.
3. Near target formation and stack widths differ by actual encoding/mode; task 3 pins literal boundaries and task 7 supplies authored execution evidence.
4. An otherwise valid checksum-recomputed cache with wrong context must fail loaded-image validation; task 4 owns this case.
5. Effective PE mode edits, readonly cache reopen and simultaneous 32/64 tabs must never adopt another mode's facts; tasks 5, 6 and 8 own explicit barriers and persistence tests.

## File responsibilities and interfaces

- core/include/hexlab/core/architecture.hpp: existing Architecture/ExecutionMode values plus DecodeContext containing architecture, mode and ByteOrder. image.hpp includes this header; enum numeric values stay unchanged.
- processors/include/hexlab/processors/decoder.hpp and new src/dispatch.cpp: ProcessorCapabilities {can_decode,max_instruction_bytes,display_name,reason}; processor_capabilities(DecodeContext) noexcept; decode_instruction(DecodeContext,span<const byte>,Address); source-compatible decode_x64 plus decode_x86_32 wrapper.
- processors instruction.hpp and x64_internal/prefixes/operands/arithmetic/flow/decode sources: explicit instruction context and mode-aware original scalar parsing. Files remain focused by existing responsibility; no duplicate decoder copy.
- analysis cache codec and recovery sources: authoritative context, canonical v2 instruction records and source-key invalidation.
- loader raw/recipe, workspace validation/listing/analysis and frontend raw dialogs/arguments: opt into fully integrated mode support.
- tests/processor_modes_tests.cpp, tests/mode_project_tests.cpp, tests/desktop_mode_tests.cpp, tests/fixtures/x86_32_oracle/: literal, integrated, native GUI and separate native execution proof.
- docs/x86-32-coverage.csv, docs/x86-32-validation.md and existing capabilities/build docs: variant-scoped evidence.
