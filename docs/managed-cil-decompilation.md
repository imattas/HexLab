# Managed CIL decompilation

The native-sized `conv.i`, `conv.u`, and checked native conversion family now
retain explicit runtime-width provenance, typed integer formulas, and managed
OverflowException guards. See
[native integer conversions](managed-cil-native-conversions.md) for the
AnyCPU rules, exceptional CFG, metadata contract, and remaining opaque cases.

Fixed-width integer `conv.ovf.i1/u1/i2/u2/i4/u4/i8/u8` and `.un` variants
require a known integer stack input and retain a typed normal conversion result
plus an exact width-aware overflow predicate on an instruction-point
`System.OverflowException` may-trap edge. The `.un` suffix interprets the input
as unsigned; without `.un`, CIL's signed-source interpretation is used. Narrow
results are extended to the CIL I4 stack category after checked truncation.
Exception-handler routing remains a conservative runtime continuation and
leaves the result incomplete. Floating, reference, unknown, or invalid-width
inputs fail closed; checked floating conversions and complete CLR exception
dispatch remain unsupported.

## Indirect pointer memory subset

The lifter models scalar `ldind.*` and `stind.*` families as explicit memory operations. Loads consume one address and emit a read intrinsic with a typed result: signed/unsigned 8-, 16-, and 32-bit loads use the CIL evaluation-stack I4 category, 64-bit loads use I8, `r4`/`r8` use their floating widths, `ref` yields a managed reference, and native `i` uses the explicit runtime width when established, otherwise retaining width zero. Stores consume address and value and emit write intrinsics. `ldobj`, `stobj`, `initobj`, and `cpobj` validate and retain TypeDef, TypeRef, or TypeSpec tokens and emit explicit memory intrinsics with the correct stack effects. `ldobj` keeps an unknown result type; `cpobj` uses an unknown memory effect because the token's size and alias behavior are unresolved. `cpblk` and `initblk` preserve destination, source/fill value, and dynamic size operands; `cpblk` has an unknown read/write effect and `initblk` a write effect. Object and block operations mark the decompilation incomplete and add a diagnostic because aggregate sizes, exact value types, dynamic extent, and alias behavior are unresolved. Stack underflow and `max_stack` violations remain malformed errors. The lifter does not prove that an address is a managed byref, validate a stored value against the pointed-to type, resolve aggregate layouts, evaluate memory, or infer alias relationships.

## Field access subset

`ldfld`, `stfld`, `ldsfld`, and `stsfld` are lifted when their operand resolves to an in-module FieldDef or MemberRef field. The resolver retains declaring type/name, signature, and token; FieldDef flags are also retained. The lifter verifies static-vs-instance opcode use against the FieldDef static flag, carries the object expression for instance access, types loads when the signature maps to a supported `ValueType`, and emits explicit read/write memory-effect intrinsics. `ldflda` and `ldsflda` also preserve the field identity and produce a typed managed-reference stack value. Since the common IR does not resolve CLR field layout or model escaped managed-reference aliases, these address operations mark the result incomplete and carry no fabricated byte offset. Field tokens are included in `referenced_tokens`. Unresolved signatures and external identities are unsupported explicitly; they are never guessed. This remains a bounded lifter rather than CLR verification, so receiver assignability and store value compatibility are not proven.

`hexlab::decompiler::decompile_managed_method` converts a decoded `ManagedMethodAnalysis` into the common lifted-function IR and structured C-like pseudocode. It partitions IL at branch leaders, builds basic blocks and branch/fallthrough edges, simulates the evaluation stack within each block, and represents arguments, locals, fixed-width constants, arithmetic, comparisons, calls, and returns as IR expressions/statements. Method and call metadata tokens remain in the output's `referenced_tokens` list and in call names.

The floating-point slice preserves `ldc.r4`/`ldc.r8` constants as exact IEEE bit patterns, types floating stack values at 32 or 64 bits, and lifts `conv.r4`, `conv.r8`, and `conv.r.un` with explicit integer-to-float or float-width conversion operations. Floating add/subtract/multiply/divide, remainder, equality, ordered comparisons, and unordered `cgt.un`/`clt.un` and comparison branches retain floating types and unordered-NaN behavior. Exact literal bit patterns render as `bitcast_f32`/`bitcast_f64`; floating remainder and unordered predicates render as explicit operations. Unsupported or mismatched floating stack types stop lifting rather than being coerced to integers. Native-sized conversions are covered by the separate native-conversion slice; checked conversions from floating inputs remain unsupported.

Call stack effects use decoded `ManagedCallSignature` metadata keyed by token, with an explicit map available to override metadata resolution. The decompilation result preserves the method's declaring-type and method generic parameter records, including flags and constraint tokens. Call arguments and results inherit supported types from resolved metadata signatures. Closed generic TypeSpec parents and MethodSpec method arguments are substituted for call typing; open generic owners and unresolved substitutions remain unknown, and the common IR does not print complete generic source types. Invalid instruction boundaries, stack underflow, and excess values at `ret` fail with `malformed`. Exception-handling sections are retained within the bounded behavior described below; unrelated extra method-data sections are rejected as unsupported.

Method signatures now retain their decoded return and parameter signature trees. `ELEMENT_TYPE_VAR` and `ELEMENT_TYPE_MVAR` nodes carry the compressed generic parameter index; generic instances retain their coded type identity, class/value marker, and ordered type arguments. For a `MethodSpec` token, `method_spec_arguments` retains each instantiation type, and that token's resolved call signature preserves the base method's signature and generic arity. The CIL lifter uses the signature for stack effects and supported call typing. MethodSpec arguments substitute MVAR nodes and closed generic TypeSpec parent arguments substitute VAR nodes for call argument/result categories. TypeDefOrRef coded indexes are preserved alongside resolved tokens and names when in-image metadata provides them. Constraint rows likewise remain raw metadata tokens; no constraint semantics are inferred.

Method-level P/Invoke mappings from `ImplMap` are retained on their `MethodDef` records, including raw mapping flags, the imported entry-point name, the `ModuleRef` name and token. The parser validates the `MemberForwarded` coded index, module and string heap bounds, unique mapping ownership, defined flag masks, and agreement between method mappings and `PInvokeImpl` flags. The `methods` CLI view prints each retained native import. `ImplMap` rows targeting fields are range-checked but are not exposed; import-name fallback rules, native ABI marshalling, library resolution, and invocation semantics remain outside this metadata view.

Catch clauses resolve in-image TypeDef and TypeRef tokens to fully qualified names for lifted predicates and handler markers. The original token remains in each predicate and in `referenced_tokens`. For a TypeRef scoped to an AssemblyRef, the method view also retains the exact assembly name, four-part version, culture, flags, and public-key-or-token bytes; catch predicates and handler markers expose those values so same-named types from different assemblies remain distinguishable. TypeSpec names and absent tokens remain unresolved. Preserving an external identity does not bind it to a loaded definition or prove CLR catch assignability.

This is a bounded semantic slice, not a CLR verifier. It supports argument/local loads and stores, integer and floating constants, `ldnull`, metadata-resolved `ldstr` constants, `dup`, `pop`, integer and floating arithmetic, comparisons, fixed-width unchecked integer and floating conversions, basic conditional/unconditional branches, signature-resolved `call`, `callvirt`, and `newobj`, `ret`, and `throw`. The array subset includes `newarr`, `ldlen`, `ldelema`, fixed-width `ldelem.*`/`stelem.*`, and token-typed `ldelem`/`stelem`. Token-typed array operations preserve their type token in explicit memory intrinsics. The method inspector proves reference results for local class TypeDefs, explicit class TypeSpecs, and a small set of core-library TypeRefs; other token element types remain stack-type-unknown and mark decompilation incomplete. The `methods` CLI view prints token operands for these opcodes. Allocation, length, element-address, element-load, and element-store operations are explicit intrinsics with memory effects; primitive load result widths are preserved. Native-width integer and array-length values use the method's explicit runtime width, retaining width zero for unresolved AnyCPU or absent runtime context. `ldstr` values retain their original token and render as escaped string literals; see [Managed CIL user strings](managed-cil-user-strings.md). Integer conversions preserve their I4/I8 evaluation-stack result width. Narrow integer conversions retain an explicit truncate followed by sign or zero extension when the input type is known; when it is unknown or non-integer, the IR retains a named `cil_conv_i1`/`cil_conv_u1`-style operation instead of inventing source semantics. Floating constants preserve their raw IEEE bits, and `conv.r4`, `conv.r8`, and `conv.r.un` preserve explicit source/result widths. Unordered comparisons use explicit unordered predicates so NaN behavior is not lost. `leave` clears the evaluation stack and, when exiting nested finally-protected try regions, follows explicit continuation IDs through applicable finally handlers in inner-to-outer order before reaching its original target. The lifted CFG contains the corresponding `endfinally` dispatch edges. A leave does not run a finally whose try region contains its target. Catch, filter, and finally region bounds become block boundaries and receive typed intrinsic markers; catch and filter entries begin with an `exception` value. Each instruction in a protected try has a conservative exceptional edge to a synthetic ordered dispatcher, kept separate from ordinary stack flow; this over-approximates throwability. Exceptional successors enter synthetic dispatch blocks that preserve catch-clause order with opaque runtime type-match predicates and route through applicable nested finally handlers. Filter evaluation retains the original exception search: `endfilter` routes by its result, while an explicit throw or conservatively possible exception in filter code resets the result to false and resumes ordered search by the active filter continuation. Nested exception regions and `rethrow` inside filters remain unsupported. `rethrow` elsewhere is modeled only inside a catch or filter handler. CLR type assignability and exact throwability remain runtime-dependent, so protected instructions still use conservative possible-throw edges; fault clauses run only on exceptional unwind, and this CFG is not a CLR runtime simulator. Ambiguous overlapping finally regions remain unsupported.

Stack values may flow across modeled block edges, including loop backedges. A bounded worklist first propagates evaluation-stack depth and exact IR `ValueType` shapes through the CFG; each analyzed block shape is established once, while later backedge inputs must match it exactly. Conflicting depth or types are malformed. The emission pass preassigns block-edge stack values and creates explicit SSA phis at multi-predecessor joins, including loop headers, so forward/backedge inputs need no speculative expressions. A 2,000,000-transfer budget, 1,000,000-edge bound, 4,000,000 aggregate stack-cell bound, declared `max_stack` (or a conservative 1,024-entry bound when unavailable), and the 256-slot virtual-register limit keep this analysis bounded. Unreachable components are seeded with an empty stack for conservative local analysis; unsupported instructions terminate stack propagation rather than inventing values. `switch` decodes its bounded target table, pops one selector, creates case leaders and dispatch edges, and preserves ordered zero-based case values plus the fallthrough default in the common switch-dispatch IR. It does not yet resolve actual argument/local types or names, MemberRef fields, full field layout/alias semantics, checked floating/unknown-input conversions, complete generics, or runtime-specific instructions. Unknown and known-but-unsupported opcodes are retained as explicit unsupported IR markers and mark the result incomplete; unsupported stack effects return an error instead of producing guessed pseudocode. Basic blocks are limited to 100,000 and instructions to one million, in addition to the loader's per-method IL bound.

Validation: `tests/decompiler/cil_decompiler_tests.cpp` checks local/argument flow, integer arithmetic, conditional CFG recovery and returns, compatible conditional-path stack merging and phi inputs, malformed depth/type merges, token-preserving signature-resolved calls, malformed stack underflow, unknown opcodes, and missing call-signature rejection.

## Checked I4/I8 arithmetic

`add.ovf`, `add.ovf.un`, `sub.ovf`, `sub.ovf.un`, `mul.ovf`, and `mul.ovf.un` are decoded and lifted for matching 32- or 64-bit integer operands. The result retains the CIL stack width, and an instruction-point `System.OverflowException` may-trap edge carries a signed sign-bit predicate, unsigned wraparound comparison, or a width-specific multiply-overflow predicate (`cil_smul_overflow_i32/i64` or `cil_umul_overflow_i32/i64`). The multiply predicate is true exactly when the mathematical product is outside the signed or unsigned destination range selected by the opcode. The `.un` suffix selects unsigned overflow interpretation; result bits retain the low I4/I8-width product. Floating, reference, mismatched-width, and unresolved operands fail closed. Exception-handler dispatch remains conservative; therefore the overall decompilation remains incomplete when one of these checked operations is present.
