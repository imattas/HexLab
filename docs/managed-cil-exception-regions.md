# Managed CIL exception regions

The managed loader preserves bounded CLR exception-handling sections on `CilMethodBody`. Small and fat clause encodings and up to sixteen aligned sections are supported. The method-wide clause limit is 4096, enforced before clause allocation. Each clause retains its decoded kind, protected and handler ranges, catch token or filter offset, original flags, encoding width, section offset, and clause offset. Section and clause provenance offsets are relative to the method header; IL ranges are relative to the first instruction. `data_sections` retains section kind, size, encoding, chaining flag, and its contiguous clause-index span. Optional IL-table sections remain inspectable, but the lifter rejects their unmodeled semantics even if EH clauses are also present.

`ManagedCilDecompilation` retains the complete clause vector in metadata order and exposes `exception_regions`, grouping clause indexes by identical protected-try ranges. Clients can inspect this information independently of the pseudocode and synthetic CFG. Region groups are listed deterministically by protected offset and length. Handler search executes nested tries before containing tries, and preserves metadata order among clauses of the same try. Consequently, the physical order of nested groups across EH sections does not change search precedence.

Before constructing a dispatch graph, the lifter validates nonempty bounded ranges, catch-token tags, instruction boundaries, and contiguous instruction coverage. An interval sweep accepts disjoint scopes, identical protected tries, and strict lexical containment. Each nested try, its handlers, and its filters must share one enclosing scope. Crossing intervals, aliased handler/filter ranges, and constructs whose nested try and handlers belong to different outer scopes are rejected as unsupported. A clause's handler or filter overlapping its own try is malformed. Filters and catches can be nested in an enclosing try or catch handler; additional EH constructs inside a filter, finally, or fault handler are unsupported. In particular, nested EH inside finally/fault requires saved unwind state and must not overwrite the active continuation register.

Try, handler, filter, and region-end offsets become basic-block boundaries. Terminating instructions split subsequent dead code into separate blocks. Every `endfinally` is also a block boundary, so a multi-instruction handler has an identifiable continuation source. Catch and filter-handler entries begin with one opaque managed exception reference; filter code begins with the same reference. Finally and fault entries begin with an empty evaluation stack. Protected-try entries require an empty stack, and declared zero `max_stack` cannot accommodate a catch/filter entry. Local and argument values remain opaque according to the ordinary CIL lifting rules.

`endfilter` consumes exactly one result and rejects a known result type other than int32 or a comparison boolean; an unknown result type remains opaque. Nonzero selects the filter's handler, and zero continues clause search. An explicit `throw` or conservatively possible exception during filter execution follows its false-result continuation and preserves search for the original exception. `rethrow` in filter code remains unsupported. Elsewhere, `rethrow` requires a catch/filter handler and an empty evaluation stack. `endfinally` requires an enclosing finally/fault handler and an empty evaluation stack. `ret` cannot exit a protected try, filter, or handler; `leave` cannot exit a finally/fault handler. Ordinary fallthrough out of a protected try, into or out of a handler/filter, or past the end of an EH method is malformed. Existing explicit branches or switches crossing EH boundaries without `leave`, and `leave` transfers entering protected regions or handlers, remain unsupported.

Normal `leave` clears the evaluation stack and executes exited finally handlers from inner to outer. It does not run faults or a finally whose protected try still contains the target. Each route assigns a continuation ID, enters the innermost finally, and uses `endfinally` dispatch to reach outer finally handlers and the original target. A finally/fault needed by a route must contain a modeled `endfinally` instruction. Ambiguous unwind ordering remains unsupported.

Exceptional control flow conservatively considers every instruction in protected tries and handlers, and explicit `throw`/`rethrow` elsewhere. Handler instructions with no enclosing protected try route to an explicit unhandled terminal rather than losing their exceptional exit. Synthetic dispatch preserves nested search precedence and sibling clause order. Opaque `exception_matches_type_token(...)` or named predicates select catches; filters execute before unwind. Once a handler is selected, exited finally and fault handlers run in inner-to-outer order. No-match routes unwind all enclosing finally/fault handlers before `exception_unhandled`. Continuation IDs distinguish exceptional routes from normal `leave` routes. Possible exceptions are over-approximated even for instructions that do not actually throw.

Each instruction covered by a try, handler, or filter is a separate lifted source block. This keeps an exceptional predecessor tied to one IL instruction. Exceptional memory edges select that instruction's input memory version for effects that do not mutate memory; calls and stores use an explicit unknown memory effect because an exception can follow a partial side effect. The current common IR does not give CIL locals and arguments SSA versions: `ldloc`/`ldarg` values remain opaque names and stores remain intrinsic statements. Their textual local state is therefore not an instruction-indexed SSA snapshot. Managed-address operations such as `ldloca`/`ldarga` are not lifted, and opaque `Store`/`Call` statements on exceptional edges fail closed. Consumers must not treat CIL local values as proven exception-point snapshots.

For TypeDef/TypeRef catch tokens found in the metadata catalog, handler markers and catch predicates include fully qualified names while retaining tokens. TypeSpec and absent catalog tokens remain token-only. Exact thrown type is tracked for a straight-line `newobj` followed by `throw`, allowing `nop` and decoded `castclass` wrappers, or one `stloc`/matching `ldloc` round trip with no intervening operation that changes the local. Explicit control-flow entries, method/EH boundaries, and terminal continuations invalidate the trace; synthetic per-instruction exception-source splits do not. A successful `castclass` preserves the object's runtime identity on the path reaching `throw`. Dispatch specializes only when exact-token equality or validated in-module assignability proves a catch match; unknown or external type edges retain opaque predicates. Other local flows, merged values, `rethrow`, and incidental instruction exceptions remain opaque.

Pseudocode begins with a readable EH legend giving each protected range, metadata clause index, ordered catch/filter/finally/fault clauses, handler/filter extents, and handler-entry stack contract. Ranges are half-open. A conservative lexical recognizer can now render one simple `try`/`catch` or `try`/`finally` form below this legend. All other successfully lifted EH methods retain labeled dispatch, exception edges, and continuation switches with `pseudocode.used_fallback = true` and a specific `fallback_reason`.

The reconstructed subset requires all of the following:

- Exactly one protected-region group and one clause, either a catch or a finally.
- The handler immediately follows its protected try, and an instruction-aligned continuation follows the handler. An optional straight-line prologue can precede the try.
- The try ends in exactly one `leave`/`leave.s` targeting the handler-end continuation. A catch ends in its own `leave` to that same continuation; a finally ends in one terminal `endfinally`.
- The continuation is straight-line code ending in the method's only `ret`, at the end of the IL body.
- No internal branches, switches, explicit `throw`/`rethrow`, filters, faults, unreachable blocks, unsupported instructions, or stack/memory phis occur in the method.
- Real basic-block boundaries carry empty evaluation stacks, except the catch entry's single managed exception reference. The stack must already be empty before each `leave`; the renderer does not hide discarded stack values. A catch must consume its exception reference before leaving.

For those shapes, the renderer places the existing lifted statements inside lexical braces and omits only region markers, the proven terminal leaves, and their finally-continuation bookkeeping. Expressions, calls and local/argument stores use the existing statement formatter without being recomputed. Catch headers retain `type_token(0x...)` and the opaque `exception` binding; a resolved metadata name is shown only as a quoted comment. The recognizer does not infer a concrete exception object, prove that a catch will match, or replace runtime assignability with name comparisons. `finally` denotes CLR-managed normal and exceptional execution, rather than a duplicated ordinary call to the handler.

Structured output sets `pseudocode.used_fallback = false` only for presentation. The complete original `lifted` CFG, including conservative possible-throw edges, synthetic catch search, unhandled terminals and exceptional/normal finally continuation routes, remains available unchanged. No synthetic dispatch blocks are deleted or rewritten. Every EH method still has `complete = false`: runtime exception identity, complete assignability and assembly binding, implicit runtime faults, and full CLR unwind semantics are not simulated.

Multiple catches, valid nested regions, nonadjacent layouts, differing leave targets, internal conditionals/loops, nonempty leave stacks and other unsupported presentation shapes keep the explicit CFG fallback. Filters and faults always use that representation. Crossing scopes and other malformed or unsupported topologies still fail the existing topology validation before a lifted CFG is available; the renderer does not bypass those checks to manufacture structured output. The existing 16 MiB IL-body, one-million instruction, 100,000 real-block, clause, and stack-analysis limits continue to bound reconstruction.

The catch-entry object, nested search, filter, and unwind rules are described by ECMA-335 Partition I, sections 12.4.2.5-12.4.2.6, and Partition III's `endfilter`, `endfinally`, `leave`, `ret`, and `rethrow` definitions ([ECMA-335, 6th edition](https://ecma-international.org/wp-content/uploads/ECMA-335_6th_edition_june_2012.pdf)).

The public loader and decompiler result structures carry this metadata, so consumers must be rebuilt against both updated headers. The relevant library targets are `hexlab_loaders` and `hexlab_decompiler`.
