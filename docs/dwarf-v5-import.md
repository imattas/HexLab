# ELF DWARF v5 import

Structure and union members with constant `DW_AT_bit_size` are imported when their integral storage type and bit position are representable. `DW_AT_data_bit_offset` is preferred and maps the bit range to a storage-unit byte offset plus an LSB-relative position; legacy `DW_AT_bit_offset` is converted using the little-endian storage-unit convention. Widths and ranges are checked against the storage type and the aggregate layout validator rejects overlapping or out-of-bounds fields. Dynamic bit positions, missing/unsized or non-integral storage, fields crossing the modeled storage unit, and unsupported endian-specific layouts are rejected rather than guessed. The ELF DIE importer currently accepts little-endian input only.


The `.debug_info` stream accepts DWARF32 and DWARF64 initial lengths for supported v4/v5 compile and type units. It checks the declared length against remaining section bytes before narrowing to a host span, uses the corresponding 4- or 8-byte offset width for abbreviation offsets, v5 type-DIE offsets, and fixed-width offset forms (`strp`, `line_strp`, `strp_sup`, `ref_addr`, and `sec_offset`). The importer builds a bounded section-wide DIE-offset index across all supplied units before resolving supported `DW_FORM_ref_addr` type references, so a type in a later compilation unit can be resolved without publishing partial results. A target offset inside the supplied `.debug_info` bytes that does not identify a DIE is malformed; an offset outside those bytes is treated as a possible external/package contribution and requires the applicable explicit resolver or returns unsupported. The v5 `.debug_str_offsets`, `.debug_addr`, `.debug_loclists`, and `.debug_rnglists` contribution readers accept both initial-length formats and validate each contribution header and extent. Offset tables use the contribution's 4- or 8-byte offset width; `.debug_addr` entries continue to use the unit's address size. The line-table importer accepts DWARF32 and DWARF64 units for supported versions 2 through 5, using the declared offset width for prologue lengths and v5 `DW_FORM_strp`/`DW_FORM_line_strp` directory and file entries. DWP index readers remain DWARF32-only.

Structure members in both v4 and v5 accept `DW_AT_data_member_location` as a nonnegative constant form or a bounded constant expression made from DW_OP_lit*, DW_OP_constu/consts, DW_OP_plus, and DW_OP_plus_uconst. The expression must leave exactly one nonnegative value; register, address, dereference, subtraction, and other dynamic operations remain unsupported. Supported v5 additions are compile-unit headers, standalone type-unit headers (`DW_UT_type`) with checked signature/type-DIE offset, abbreviation `DW_FORM_implicit_const`, `DW_FORM_line_strp`, indexed `DW_FORM_strx`/`DW_FORM_addrx` families, and a bounded `.debug_loclists` subset for variable locations. Type-unit DIEs use the same bounded type decoder. Before resolving DIEs, the importer makes a bounded pass over unit lengths and headers, then orders units by their cross-unit dependencies. `DW_FORM_ref_sig8` resolves to a type DIE identified by a unique type-unit signature even when the type unit appears later than its referring compile unit or type unit. Duplicate signatures are malformed and missing signatures return an explicit unsupported diagnostic. Signature dependencies are topologically ordered with ordinary `DW_FORM_ref_addr` dependencies; dependency cycles fail closed as unsupported. Unit-relative references resolve within their owning unit. `DW_FORM_ref_addr` resolves within the current unit or across ordinary compile units for supported type DIEs and subprogram `DW_AT_specification`/`DW_AT_abstract_origin` inheritance. A retained per-unit DIE index is built before resolution, and cross-unit dependencies are topologically ordered so references may target later units. Function inheritance requires a complete named declaration whose return and parameter types resolve in the same import. Non-subprogram targets for function inheritance and other cross-unit non-type references are rejected. Indexed string/address forms require the unit root's `DW_AT_str_offsets_base` or `DW_AT_addr_base`; contribution version, header width, address size, entry bounds, index arithmetic, string offsets, and termination are checked before the import result is published. Indexed strings resolve through `.debug_str`; `DW_FORM_line_strp` resolves through `.debug_line_str`. `DW_FORM_strp_sup` resolves through ELF `.debug_str_sup` when that section is present. Supplementary type references require an explicit identity-backed resolver or selected package, as described below; split-unit pairing is described below. The import remains little-endian for ELF DIE data.

The location-list subset accepts variable `DW_FORM_sec_offset` and `DW_FORM_loclistx` (with `DW_AT_loclists_base`) references, and `DW_LLE_base_address`, `DW_LLE_base_addressx`, `DW_LLE_offset_pair`, `DW_LLE_start_end`, `DW_LLE_start_length`, `DW_LLE_startx_endx`, `DW_LLE_startx_length`, and `DW_LLE_default_location` entries. Indexed address entries resolve through the unit's `DW_AT_addr_base` in a validated DWARF v5 `.debug_addr` contribution; indices, range ordering, and address-length overflow are checked. Both DWARF32 and DWARF64 contributions are supported for these indexed tables and for the bounded location/range-list subsets. It preserves each explicit half-open PC range and optional default expression with raw expression bytes and decoded operations through ELF metadata, workspace import, project persistence, undo/redo, and the PC-aware Variables view. Explicit ranges take precedence; the default is selected when no explicit range covers the requested PC, including at `UINT64_MAX`. The default expression is stored in the existing range record using the reserved empty `[UINT64_MAX, UINT64_MAX)` sentinel; this cannot collide with a valid nonempty range, and storage validation permits it at most once. The caller-driven location API selects the range at the requested PC and can evaluate scalar expressions or retain `DW_OP_piece`/`DW_OP_bit_piece` fragments through `evaluate_imported_variable_location_sequence`; register and memory access is supplied by the caller. The importer and desktop view do not evaluate variables automatically. Other location-list opcodes remain unsupported; a list is never flattened to an arbitrary PC.

Ranged subprogram DIEs inherit missing names, return types, and parameter lists
from same-unit `DW_AT_specification` or `DW_AT_abstract_origin` targets. They can
also inherit those fields from a complete named subprogram declaration in any
ordinary compile unit through `DW_FORM_ref_addr`, including a later unit.
Already-resolved subprogram summaries can be carried through a chain of
specification/origin edges; return and parameter types are resolved before
dependent units. Declarations
whose signature cannot be represented remain unsupported. Cycles and references
to non-subprogram DIEs are malformed.

The symbols API `evaluate_imported_variable_location(variable, pc, context)` selects a matching half-open location range and evaluates its already-decoded operations. For an un-ranged variable it evaluates the direct expression, then falls back to a direct absolute address when present. For a ranged variable, an explicit matching range is selected first, then its default entry if present; otherwise it never falls back to its address or another range when the requested PC is uncovered. The result is a register location, memory address, or scalar value as classified by the expression. Register values, frame/CFA values, and memory reads come only from the caller callbacks; this API performs no process access. Missing locations, unmatched PCs, and unavailable runtime inputs return explicit errors.

The scalar evaluator supports literals/constants, direct and base-register locations, frame-base/CFA-relative addresses, bounded dereferences, `DW_OP_nop`, stack manipulation (`dup`, `drop`, `over`, `pick`, `swap`, `rot`), and fixed-width integer arithmetic, bitwise operations, and shifts. Signed division/remainder use the target address width; arithmetic wraps to that width, while division by zero, out-of-width shifts, stack underflow, and arithmetic on an unmaterialized register location return explicit errors. Branching expressions, pieces in the scalar entry point, implicit values, TLS, and entry-value operations remain unsupported. Composite pieces use `evaluate_location_expression_sequence`, which shares the 65,536 executed-operation and 4,096 memory-read budgets across every piece in a composite expression. This prevents many individually small pieces from multiplying the evaluator's work limits. This is a bounded subset of the DWARF expression language; the caller owns process state, target endianness in the memory callback, and fault handling.

DWARF v4 remains source-compatible through `import_dwarf_v4`. Existing v2â€“v5 line-program import remains separate; its line-table v5 header, content/form directory and file descriptors, and row opcodes are covered by `dwarf_line` tests. The ELF loader's existing line path continues to preserve those rows independently of type/symbol import.

The ELF reader validates the bounded DWARF v5 `.debug_sup` descriptor (version, role flag, NUL-terminated filename, and ULEB-sized checksum) and discovers `.debug_str_sup` for `DW_FORM_strp_sup`. Filenames are metadata hints only: the loader/importer never opens them. `DW_FORM_ref_sup4` and `DW_FORM_ref_sup8` are resolved through a caller-owned `ElfLoadOptions::dwarf_supplementary_resolver` (or the equivalent `DwarfSections::supplementary_type_resolver`), or through `ElfLoadOptions::dwarf_supplementary_package` when no callback is supplied. The package option is an explicitly selected `ByteStorage`; the loader verifies its ELF class and byte order against the application and checks its supplementary `.debug_sup` checksum against the application's descriptor, then uses `.debug_tu_index` to locate exactly one type-unit contribution containing the requested section offset. The type-unit signature must match its TU-index row; `DW_UT_split_type` is parsed as a type unit with a signature and type offset, without a DWO ID. A `DW_TAG_type_unit` wrapper root is accepted, and `DW_FORM_strx` may use the start of that split type unit's supplied `.debug_str_offsets.dwo` contribution when no explicit base is present; this implicit base does not apply to other units. Only a type DIE imported from that contribution is returned. Package file and decoded index allocations are charged against `dwarf_supplementary_max_bytes` before further package reads/publication; normal importer request and encoded-type budgets still apply. Requests outside indexed contributions, ambiguous contribution ranges, unsupported type-unit forms, or checksum mismatches fail closed. No filename lookup occurs. A custom callback remains available for other supplementary-object layouts and owns its own identity-attestation contract.

Automatic supplementary DIE file discovery and supplementary DIE forms without an explicit resolver or supplied package, cross-contribution `DW_FORM_ref_addr` references without an explicit resolver, cyclic cross-contribution dependency chains, relocated sections, segmented `.debug_addr`, range-list forms outside the bounded DWP split-unit subset, and forms not listed above remain explicitly unsupported. Skeleton/split-unit pairing and supported DWO/DWP contribution import are described below. Indexed bases must point to the first entry of a standard v5 contribution. Unsupported or malformed debug metadata produces a loader diagnostic and does not prevent loading the ELF image; an unsuccessful import is never published as a partial `ImportResult`.

## Split DWARF pairing

For references into a different, already-selected DWO/DWP contribution, callers may set `DwarfSections::cross_contribution_die_resolver`. The resolver must look up the exact target in the selected CU or TU package index and attest the matching row signature and INFO contribution range. The importer independently checks the returned absolute offset, contribution-relative DIE offset and extent, index kind, DIE kind, encoded type size, and per-import request/byte budgets. Type references may resolve only to type DIEs; `DW_AT_specification` and `DW_AT_abstract_origin` inheritance may resolve only to named subprogram summaries with function types. `import_dwarf_package_unit` and `make_dwarf_package_type_signature_resolver` have overloads that accept this callback. The callback is caller-owned, performs no filename lookup, and must maintain an active-offset set to reject cycles across nested contribution imports. Other non-type DIE references and automatic contribution discovery remain unsupported.

The bounded v5 unit-header reader recognizes compile, type, skeleton, split-compile, and split-type units. Skeleton headers provide a 64-bit DWO ID; root `DW_AT_dwo_name` and `DW_AT_comp_dir` values are passed as hints to the optional `DwarfSplitUnitResolver`. The ID is the pairing key, and repeated skeleton IDs are rejected. If no name or resolver is available, the primary ELF import is retained and a diagnostic is attached to `ImportResult::diagnostics`; ELF loading forwards these as partial-load diagnostics.

`load_elf(storage, options, stop)` exposes the resolver through `ElfLoadOptions::dwarf_split_resolver`. The callback owns discovery and parsing, so it can resolve a standalone `.dwo` or extract a DWP contribution without giving the importer authority to open a path embedded in the input. For a DWO contribution, the callback should construct `DwarfSections` from that object's matching `.debug_info.dwo`, `.debug_abbrev.dwo`, and applicable string/address sections, set `expected_split_dwo_id` to the request ID, call `import_dwarf`, and return the result. The importer rejects a contribution containing a non-split compile unit, a different ID, or a result whose reported ID does not match the skeleton. Resolver I/O, unsupported-format, and bounds failures become diagnostics; cancellation and other errors abort the import.

For standalone ELF DWO files, `make_elf_dwo_resolver` adapts a caller-owned `ElfDwoStorageResolver` into this callback, and `import_elf_dwo` imports one selected DWO directly. The storage callback receives the DWO ID plus name and compilation-directory hints; only that callback chooses and opens storage. The helper requires `.debug_info.dwo` and `.debug_abbrev.dwo`, then optionally consumes `.debug_str.dwo`, `.debug_str_offsets.dwo`, `.debug_addr.dwo`, `.debug_line_str.dwo`, `.debug_loclists.dwo`, `.debug_rnglists.dwo`, and `.debug_line.dwo`. It checks the split unit's DWO ID and address size against the skeleton, and caps section plus imported-result accounting at the configured metadata limit (64 MiB by default). It supports little-endian ELF and the existing bounded DWARF v5 split-compile forms, including DWARF64 DIE unit streams and indexed/list contribution headers; ELF zlib-compressed sections are expanded under the loader budget (see [compressed ELF DWARF](elf-dwarf-compression.md)); relocated sections, unsupported forms, and references into other DWO files remain unsupported.

DWP container remains delegated to the callback for separate package files, but the symbols library parses DWARF v5 CU and TU package indexes. `parse_dwarf_package_index(bytes, kind, little_endian, stop, limits)` validates the version-5 header, column IDs, power-of-two hash slots, load-factor bound, empty/used slot encoding, 1-based row mapping, duplicate signatures, and all table extents before publishing a parsed index. The parser accepts only section IDs defined for the selected v5 CU or TU index and requires INFO and ABBREV columns. It is format-agnostic: callers provide the index bytes and source-section spans, and it performs no ELF lookup or file access. For a split CU resolver, `find_dwarf_package_contribution` looks up the skeleton's `dwo_id`, and `import_dwarf_package_unit` maps INFO, ABBREV, ADDR, LOCLISTS, STR_OFFSETS, LINE, and RNGLISTS contribution slices into the bounded consumers, supplies shared `.debug_str.dwo` and optional `.debug_line_str.dwo`, and verifies the expected DWO ID. Split-unit range lists accept `DW_FORM_sec_offset` and `DW_FORM_rnglistx` with the supported DW_RLE base-address, start/end, start/length, indexed-address, and offset-pair entries; each list is capped at 4,096 ranges and retained on its imported function symbol. Line contributions use the existing DWARF v5 line interpreter, with at most 4,000,000 rows, bounded `.debug_str`/`.debug_line_str` references, and the ELF byte order. Macro contributions remain available through the package lookup API but are not interpreted.

When an ELF contains `.debug_cu_index` plus matching package sections, `load_elf` builds this resolver directly from the ELF section table if no caller resolver was supplied. It selects each row by the skeleton DWO ID, imports its DIE/type/address/location/range data, and retains DWO line rows in the ELF source-line metadata. External `.dwp` selection remains caller-owned: the loader does not open paths named by DWARF data. Standard and GNU zlib-compressed package sections are expanded under the shared ELF metadata budget (see [compressed ELF DWARF](elf-dwarf-compression.md)). Unsupported range-list opcodes, missing address bases, supplementary DIE offsets outside the supplied package's indexed type contributions, and relocation-dependent forms remain explicit failures or partial-load diagnostics.

The ELF loader discovers an embedded `.debug_tu_index` (or `.debug_tu_index.dwo`) independently of `.debug_cu_index`. Primary `.debug_info` imports can therefore resolve `DW_FORM_ref_sig8` into the same ELF's indexed `.debug_info.dwo` type contributions, including later contributions and packages containing only a TU index. A caller-provided split-unit resolver does not disable this primary type-signature path. The `.debug_info` section itself is still required to initiate ELF type/symbol import; a standalone DWP without it must be selected by a caller-owned resolver or as a supplementary package.

GNU DWARF4 split objects using DWP index version 2 are supported for compile-unit and type-unit contributions. The parser applies the v2 section-ID mapping (including `.debug_types.dwo` and legacy `.debug_loc.dwo`), matches compile units by the skeleton's `DW_AT_GNU_dwo_id`, and resolves type units by their indexed signature. Type-unit contribution headers accept DWARF32 and DWARF64 initial lengths, and the target DIE offset uses the unit's corresponding 4- or 8-byte offset width; the package index itself remains DWARF32. Version, contribution extent, signature, and target-DIE bounds are checked before type import. Mixed-version CU/TU indexes and relocated sections remain unsupported; standard and GNU zlib-compressed ELF sections are expanded by the loader.

The same bounded DWARF32/DWARF64 contribution-header handling applies when resolving type units through a version-5 TU index. Package index offset/size tables remain 32-bit as defined by the DWP format; DWARF64 controls only the unit's internal length and offset fields.

When embedded CU and TU indexes are both present, the primary import and all automatically resolved split compile units share one package signature resolver. Completed type signatures are cached; repeated uses do not reimport the contribution. The resolver allows at most 4,096 uncached requests across the whole ELF import, with an aggregate contribution-and-encoded-type byte limit equal to the ELF metadata budget remaining after package section/index reads. Both CU and TU decoded index tables, plus the sorted type-signature dispatch table, are charged before allocation. Package buffers remain owned for every resolver's lifetime. The resolver validates each contribution's embedded signature and target DIE offset and rejects cycles, missing signatures, non-type targets, and offsets outside the indexed contribution. Cross-contribution `DW_FORM_ref_addr` resolution is opt-in through the explicit DIE-summary callback described above; the signature resolver does not discover or select target contributions by itself.

`make_dwarf_package_cross_contribution_die_resolver` provides a bounded, package-index-backed resolver for `DW_FORM_ref_addr` targets in another CU contribution. It maps the absolute `.debug_info` offset to exactly one CU-index INFO range, imports that indexed contribution by its exact signature, and accepts only a supported type or subprogram DIE whose recorded section offset exactly matches the requested offset. Overlapping indexed ranges, absent targets, unsupported DIE kinds, and import failures are errors; it never guesses by name or nearby offset. It supports CU-index contributions only. A target whose own import requires an additional unresolved cross-contribution reference can still fail; callers needing recursive policies can supply their own explicit callback. The helper request and aggregate byte limits default to 4,096 and 64 MiB.

Callers may also select an external ELF DWP companion through `ElfLoadOptions::dwarf_split_debug_package`. The loader validates that it is an ET_REL object with the same ELF class and byte order, reads its bounded CU/TU indexes and indexed DWO sections, and resolves only the exact skeleton DWO ID requested by the primary `.debug_info`. A caller-supplied `dwarf_split_resolver` takes precedence; otherwise the selected external CU package takes precedence over an embedded CU package. Type-signature resolution prefers the selected external TU index and falls back to the embedded TU index by exact signature membership. Package index tables and section bytes share the loader's 64 MiB ELF metadata budget. The package is provided as caller-owned storage: the loader does not follow `DW_AT_dwo_name`, `DW_AT_comp_dir`, or any package filename to discover it. DWO objects remain supported through `dwarf_split_resolver`/`make_elf_dwo_resolver`; automatically finding `.dwo` or `.dwp` files is not implemented.

When selected external, embedded, and supplementary DWP packages expose disjoint TU signatures, the ELF loader now wires them into one bounded package catalog. Nested `DW_FORM_ref_sig8` chains may follow a type dependency from one selected package to a type unit in another, while each contribution retains its package source identity and the shared resolver enforces request, byte, ambiguity, and cycle limits. If a signature is indexed by more than one candidate package, the loader keeps the established exact-membership precedence resolver and skips the cross-package catalog rather than choosing a duplicate definition by package order. `DW_FORM_ref_addr` between selected package contributions is available only when the caller supplies an identity-verifying DIE resolver. Supplementary `DW_FORM_ref_sup4`/`DW_FORM_ref_sup8` offsets continue to use the selected supplementary resolver and verified object identity.

The explicit supplementary-package path is available to the CLI and durable project recipe. For example, `hexlab_cli inspect app --dwarf-supplementary-package app.debug` (or `project create app.hxproj --input app --dwarf-supplementary-package app.debug`) selects a caller-provided ELF DWP. The path is stored in the load recipe so reopening the project uses the same companion. The loader still verifies ELF class, byte order, the application `.debug_sup` checksum, the DWP TU index, type-unit signatures, and requested DIE offsets. It never opens the filename embedded in DWARF. The option requires an ELF input with an application `.debug_sup` descriptor; unsupported type forms, relocated sections, and automatic package discovery remain unsupported. ELF zlib-compressed sections are handled by the loader (see [compressed ELF DWARF](elf-dwarf-compression.md)).

Capture a parsed index and package section views in the existing `DwarfSplitUnitResolver`. For a skeleton request, call `find_dwarf_package_contribution(index, request.dwo_id, section_views, stop)`. The lookup follows the DWARF double-hash probe sequence, uses the 1-based row associated with the signature, and returns borrowed section spans after checking each 32-bit offset/size pair against its corresponding source section. Pass those spans and the shared `.debug_str.dwo` / optional `.debug_line_str.dwo` tables to `import_dwarf_package_unit`; the wrapper maps DIE-related contributions into `DwarfSections` and consumes LINE/RNGLISTS through the bounded line and range-list readers. The explicit ELF byte order and address size must match the split unit. The returned spans borrow the package sections and remain valid only as long as those source buffers. `TU` indexes can be parsed and looked up with the same API; their INFO contribution contains DWARF v5 split-type units. The package index parser supports little- and big-endian index words; ELF DIE import currently supports little-endian ELF only.

The default index limit is 64 MiB, with at most 8 columns, 1,000,000 rows and 2,000,000 hash slots; callers may lower these limits. Table-size arithmetic is checked before allocation, and cancellation is checked while walking hash slots and rows. Nonzero trailing bytes, malformed empty slots, duplicate rows/signatures/section IDs, unsupported section IDs, and contribution slices outside the provided package section fail explicitly. A missing package signature returns `unsupported`; the resolver may convert that into its normal partial-load diagnostic. This does not automatically discover or open external `.dwp` paths, validate package filenames, or relocate debug data. The bounded `make_dwarf_package_type_signature_resolver` API accepts a parsed TU index and the package section views, preserves the index row signatures while importing each referenced contribution on demand, and resolves `DW_FORM_ref_sig8` across split type-unit contributions. It enforces request and aggregate byte limits, verifies each row against the embedded type-unit signature and target DIE offset, caches completed signatures, and rejects active-signature cycles, missing or ambiguous signatures, out-of-contribution offsets, and non-type targets. Cross-contribution `DW_FORM_ref_addr` targets remain unsupported because DWARF package contributions are imported as separate bounded units. Package-backed ELF supplementary imports use this resolver automatically when a verified DWP package is selected. Any failed reference aborts the current import; no partial `ImportResult` is published.

The index layout and section identifiers follow DWARF v5 section 7.3.5.3 and table 7.1; the standard defines the signature table, parallel row-index table, section-ID row, and row-major offset and size tables. [DWARF v5 standard](https://dwarfstd.org/doc/DWARF5.pdf). DWO path strings are untrusted metadata hints and must be canonicalized/sandboxed by the callback before use.

The importer supports pairing only for DWARF v5 skeleton/split unit headers. A DWO without its matching skeleton must be imported with `expected_split_dwo_id`; ordinary standalone calls reject split units. DWARF64 DWP indexes remain unsupported.

Split DWO imports accept DWARF v5 split-type units in the same `.debug_info.dwo` stream as the exact-ID split compile unit. Their type signatures, resolved type graphs, and source origins are retained in `ImportResult::type_signatures`. `make_elf_dwo_type_signature_resolver` builds a bounded resolver over caller-selected `{DwoRequest, storage}` pairs. It requires unique nonzero DWO IDs and explicit 4- or 8-byte address sizes, validates each imported result against its selected DWO ID/address size and type DIE provenance, rejects duplicate signatures, and caches completed imports. Resolver calls are serialized; recursive signature requests and object-import cycles are rejected. Defaults cap the catalog at 4,096 sources, signature requests at 4,096, and selected storage plus imported result data and requested encoded types at 64 MiB, with a 64 MiB per-DWO import limit. Missing signatures return unsupported; ambiguous, malformed, or cyclic matches fail closed. No DWO path is followed automatically. A custom `DwarfTypeSignatureResolver` remains available for application-specific catalogs.


### ELF DWARF data relocations

For ordinary ELF DWARF sections, the loader applies only little-endian absolute data relocations with explicit addends: x86-64 `R_X86_64_64`, `R_X86_64_32`, `R_X86_64_32S`, and AArch64 `R_AARCH64_ABS64`/`ABS32`. Each relocation must target a loaded DWARF section, have a validated symbol table/index and field width, and reference a defined section symbol; out-of-bounds fields fail the import with a diagnostic; `R_X86_64_64` writes the ABI-defined low 64 bits, while `R_X86_64_32S` accepts only results in the signed 32-bit range and encodes their low 32 bits. Unsigned 32-bit overflow fails. Unsupported relocations targeting these sections also fail that import. Instruction/PC-relative relocations are never applied. Relocation of DWO/DWP contributions and implicit-addend REL records remains unsupported.
